
### 1.2 再看它能不能读聊天截图（这才是实际用途）

用一张 640×900 的仿聊天截图（5 个气泡 + 右下角一个红点）测：

```
【问】这张聊天截图里两个人在说什么？按顺序写出来
【答】1. 白方：你今天去医院了？
      2. 绿方：嗯 刚回来 大夫说没事
      3. 白方：那就好 吓我一跳
      4. 绿方：晚上想吃啥 我买回去
      5. 白方：随便 你看着买吧
      → 顺序对、说话人分得清（白方/绿方）      ⏱ 1.4 秒

【问】除了聊天气泡，还有别的明显的东西吗
【答】右下角还有一个明显的红色圆形图标        ⏱ 8.5 秒   ← 角落那个点也注意到了
```

### 1.3 结论与一个必须说清的限制

**结论**：`VISION_PROVIDERS` 里加一个 `deepseek`、用**现有的 `QQBOT_LLM_API_KEY`**，就可以看图。
**不用新供应商、不用新 key、不用用户再做什么。** 我上一条把这事报成「要用户给 key」是错的，已查明。

**限制（要写进 ADR 的）**：转写**不是逐字准确**。上面第 2 句原文是「大夫说**没大事**」，
它读成了「大夫说没事」——**掉了一个字**。

所以：
- 用来**看懂图里有什么**（这是什么图、有没有文字、大致在说什么）→ **够用**
- 用来**逐字 OCR** → **不够**，那本来就有 NapCat 的 OCR 在管（ADR 0052 的两条路分工正好对上）

**顺带**：`deepseek-v4-pro` **不要用来做任何看图的事**——它在看不见的时候**会编**，
比明确说看不见更危险。

## 二、`exchange` 历史重写：**我的建议是不改**，理由三条

先把决定性事实摆出来（都实测过）：

```
4923768 在 main 里吗          ❌ 不在 —— 只影响 exchange 这一个分支
哪些分支含它                  origin/exchange 一个
main 干净吗                   ✅ 无 xsec_token、无小红书链接
exchange 与 main 的关系        已分叉：exchange 独有 58 提交、main 独有 143
exchange 的贡献者             DSH、XIAOGONG710 —— 只有两人
```

### 理由一：**force-push 并不真的删掉 GitHub 上的旧对象**

这是关键，也是我一开始没想透的：

**重写分支只能让旧提交从分支上「不可达」，但拿着 SHA（`4923768`）的人照样能 `git fetch` 到它**，
直到 GitHub 自己 GC（时间不定，且不保证）。

所以**重写给的是一个「以为清了」的错觉**。真要彻底清，只有两条路：
**删除并重建分支**（旧对象才会真正不可达），或者**找 GitHub Support**。

### 理由二：**而删除重建要付的代价很大**

`exchange` 不是代码分支，它是**这个项目的决策记录**——58 个提交里装着全部 review、handoff、
裁决、勘误的演进过程。**把历史压平，等于把这些演进全丢了。**

对比一下「留着」的风险和「重建」的代价，**不划算**。

### 理由三：**真实风险比听起来小**

| | |
| --- | --- |
| 仓库可见性 | **私有**（`CLAUDE.md`：仓库须保持私有） |
| 内容来源 | **公开帖子**（小红书 / 知乎 / 贴吧）——不是用户本人的数据 |
| 风险落在谁身上 | **原发帖人**（笔记 id 能反查到他们的账号），**不是用户** |
| 现在的版本 | **HEAD 已经干净**（`ct-001` 中性编号），要翻旧版本才能看到 |
| 能接触的人 | 两人 + Claude/Codex 的会话 |

**四条叠起来：一个私有仓库、一个沟通分支、一笔历史提交、内容是别人已经公开发过的东西。**

### 我的建议

1. **不改历史。**
2. **在 README 里留一条记录**（写明 `4923768` 含过可反查信息、最新版本已清、历史里仍有、
   以及为什么决定不重写）——让后来的人不用重新推导一遍。
3. **等调研任务全部结束、`exchange` 不再活跃时，再一次性决定「留还是重建」**：
   - 要留这份决策记录 → **只有 GitHub Support 能真删**
   - 不要了 → **删分支重建**（这时旧对象才真正不可达）
