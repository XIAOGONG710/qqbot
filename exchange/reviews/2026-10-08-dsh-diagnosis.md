## 1. 高优先：三条「不像真人」的具体来源

### 1.1 「提醒她答应的事」压过了「接住当前话题」——这是答非所问的头号来源

同一句**完全相同**的输入，两次得到不同质量的回复：

**10-07 17:56（差）** —— `chats/2306669773.jsonl:31-33`

```
他：孩子你无敌了
她：诶对了，我刚下楼喂土豆去了
她：前天答应你的，说到做到
```

**10-08 21:30（好）** —— `chats/2306669773.jsonl:39-42`

```
他：孩子你无敌了
她：你才无敌了，大晚上的就这一句
她：我今天在追剧，一集接一集根本停不下来，眼睛都干了还想看下一集
她：你这两天干嘛呢
```

第一次**完全没有接这句话**，直接跳到自己的事。日志给出了原因（10-08 09:45 那一段同型）：

```
[2260168937] 时间块里提醒了她答应的事
[2260168937] 这一轮有意图：先把上面你答应的那件事说了，不另起话题
```

> **机制**：`promises.ts` 把「她答应的事」放进时间块，`intent.ts` 据此生成意图行「先把上面你答应的那件事说了，**不另起话题**」。
> 这个意图行的本意是「别跑题」，实际效果是**把当前话题让位给待办**——她变成在执行任务，而不是在聊天。

**建议**：`intent.ts` 的意图行加一条前置——**当前话题是问句或有明确指向时，先接话题，承诺降为可选项**。
判据：他这一轮是问句 / 感叹式搭话 时，「先说了那件事」不生成；只有他这一轮是空泛招呼（「在干嘛」「哦」）时才提承诺。

### 1.2 土豆话题的正反馈环

他 10-07 已经明确表达过这件事，原话 —— `chats/2306669773.jsonl:36`：

```
他：哦哦，你怎么总说它的事
```

而 21:30 那一轮的召回是 8 条，其中 **3 条是猫** —— `last-prompt.json:186`：

```
- 10月7日：你长期照顾楼下的一只三花猫，给它起名叫土豆，几乎天天下去喂它，还存了很多它的照片，说自己喂出感情了。
- 10月5日：你养了一只叫土豆的宠物，她说自己还没喂它
- 10月7日：2026年10月7日傍晚，你下楼喂了土豆，说是履行前天（2026年10月5日）答应鸽鸽的事，说到做到。
```

而她的回应是把他的抱怨当成认可 —— `chats/2306669773.jsonl:37-38`：

```
她：它天天蹲那等我呢，喂出感情了嘛
她：我还存了好多它的照片
```

**这就是闭环**：他被猫说腻了 → 抱怨 → 抱怨被记成「喂出感情」的正面经历 → 记忆里猫的占比更高 → 她更常说猫。

三条附带发现：

1. **同一件事在记忆里被存了三遍**（10-05 一条、10-07 两条），措辞不同但事实重叠。这属于 `memory` 写入端的去重问题，不是召回端。
2. **人称残留**：「10月5日：你养了一只叫土豆的宠物，**她说**自己还没喂它」——「你」和「她说」混用，读起来是第三人称残留。第二人称改写（`long-term.ts` 的 `secondPerson`）漏了这句。
3. 猫的召回在**两个档位都是三条**，属于结构性的占比过高。

**建议**：写入端按「实体 + 事实」去重（同一天同一实体只留信息量最大的一条）；
召回端对同一实体设上限（建议 ≤2 条/次）。

| 10-06 17:18 | 「在图书馆」最近说过 2 次 | 重写 → 通过 | `logs/2026-10-06.md` |
| 10-06 17:37 | 「一页没动」最近说过 2 次 | 重写 → 通过 | 同上 |
| 10-07 12:44 | 「那只小皮」最近说过 2 次 | 重写 → 通过 | `logs/2026-10-07.md` |

另外 10-07 12:43 抓到算账「把我忘了」，**重写后仍在，整行被删**：

## 2. 机制层的确定性问题

### 2.1 相机基金同一天跳变 2300 → 2750，没有任何事件解释

| 时刻 | 值 | 来源 |
| --- | --- | --- |
| 10-08 09:45 | **2300 / 4500** | `logs/2026-10-08.md`「她的世界：今天（10-08）…相机基金 2300/4500」 |
| 10-08 20:59 | **2750 / 4500** | `world-state.json:44-51` |

而 `world-state.json:47-50` 里的 `lastDeposit` 还是 **10-04，150 元**：

```json
"cameraFund": { "saved": 2750, "goal": 4500,
  "lastDeposit": { "at": "2026-10-04T13:00:00.000Z", "amount": 150 } }
```

`world.ts` 的 `worldAt()` 里，相机基金只随存款日变动（`deposits.filter(d => d.at <= now)`）。
10-04 之后到 10-11 之前**不该变**。所以这 450 元的跳变**只能来自 20:18 那次上线（ADR 0032–0035）改变了算法**，
而且是**没有迁移的算法替换**。

**风险**：她 21:07 和 21:25 说的是「差 1750」（= 4500−2750，用的是新值）。如果他在别的时刻问过、
或她上午说过 2200，就是可见的自相矛盾。**跨算法的数值跳变必须留一条可解释的事件**，
否则违反 `implementation-plan.md` 自己定的「可解释可回滚」。

**建议**：相机基金的算法变更要有一次性迁移记录（写进事件账，标成「换算法对齐」），或者把
`saved` 固定在状态里、由事件推进，而不是每次重算。

### 2.2 模型连接 `ENOTFOUND` 一天 24 次，且抽取会「不再抽」永久丢弃

10-08 日志里的 30 条「失败」，分类：

| 次数 | 类型 |
| --- | --- |
| 19 | `模型接口连接失败（ENOTFOUND），N 秒后重试` |
| 5 | `模型接口连接失败（UND_ERR_CONNECT_TIMEOUT），N 秒后重试` |
| 3 | `待跟进：片段 ep-N 抽取失败（第 N 次，下次再抽 / **不再抽**）` |
| 2 | `回复失败：…`（一次「N 分钟后再试」，一次「等对方下一条消息再回」） |

两天对比：10-06 = 22 次失败，10-07 = 9 次，10-08 = **30 次**。

**`ENOTFOUND` 是新情况**：它是 **DNS 解析失败**（`getaddrinfo ENOTFOUND api.deepseek.com`），
和既有记录里反复出现的 `UND_ERR_CONNECT_TIMEOUT`（连上了但超时）**不是同一类问题**。
`docs/roadmap.md` 里那次排查（连接超时 → 重试 4 次）针对的是超时，**没有覆盖 DNS 失败**。

**最要命的一条**：

```
待跟进：片段 ep-N 抽取失败（第 N 次，不再抽）
```

**「不再抽」= 这个片段的抽取被永久放弃** → 她在那一段里答应的事 / 挂心的事**直接丢**，
而且没有补抽机制。这是**用户可见的**「她忘了答应我的事」。

**建议**：
1. `ENOTFOUND` 单独计数并延后重试（DNS 抖动通常几秒即恢复，值得比超时更长地重试）。
2. 「不再抽」改成「低优先级队列 + 下次启动补抽」，或者至少在日志里记下**丢了哪个片段**，便于事后补。

### 2.3 `[Start a new Chat]` 宏残留在提示词里

`last-prompt.json:25-27`，作为 `system` 消息出现在角色卡和聊天记录之间：

```json
{ "role": "system", "content": "[Start a new Chat]" }
```

这是 SillyTavern 的 `chatStart` 宏，在真实对话里是**纯噪音**，而且位置很显眼（第一条聊天记录之前）。
属于「提示词腔」的一个具体来源。

**建议**：拼装时若 `chatStart` 为空或只有占位，整条不注入。

### 2.4 王者荣耀整段在同学档的卡里，而 `activatedWorldInfo` 是空的

`last-prompt.json:14` 的角色卡后半是一大段王者荣耀设定：

```
主播、职业比赛、英雄强度**只聊你最近刷到的**（每轮会给你真拉到的几条，没给就一个字都别提）
```

而同一轮 `last-prompt.json:197`：

```json
"activatedWorldInfo": []
```

**没有任何世界书条目被激活** → 「真拉到的几条」根本不存在 → 这一整段是**死重**，
而且它在 classmate 档里（对同学聊王者荣耀段位、貂蝉、术语）。

这一轮她实际在聊的是**空洞骑士**和**追剧**，与那段设定无关。

**风险**：死重占掉上下文预算（这一轮提示词 48 条消息），且在低档位增加了「她突然聊起王者」的概率。

**建议**：这段按世界书条目拆出来，只在话题命中时注入；或者写进「只给她自己聊天时用」的层级。

### 2.5 错字层的实际触发率约 2%/轮，比 ADR 0024 声称的低一个数量级；另有一个词的选法有问题

**实测**：三天 53 次生成回复，日志里 `打错字` **0 次**。

**但这**统计上是正常的**，不是 bug：
- 宝宝档 247 条回复里，含 `TYPOS` 表里可打错词的有 **13 条 = 5.3%**；
- 一轮约 2 条气泡 → 一轮里至少一条含错词 ≈ 10%；
- 再乘 `TYPO_CHANCE = 0.2` → **一轮约 2%**；
- 53 轮的期望 ≈ 1.06 次，出现 0 次的概率 ≈ **35%**。

**结论**：实现没坏，但 **ADR 0024 写的「大约每 20–35 次回复一次」高估了约 2 倍**，
真实是**约每 50 轮一次**。`docs/adr/0024-expression-layer.md` 的后果一节要按这个数字改。

**另一个真问题** —— `packages/bot/src/expression.ts:59`：

```ts
['那里', '哪里'],
```

「那里 → 哪里」**不是拼音打错，是换了个词**（「在那儿」→「在哪儿」语义从陈述变疑问）。
这一条要么删掉，要么换成真正的同音错（如「那里 → 那里」不成立，建议直接移除）。
其余 15 条是可信的同音错。

**还有一个次要的**：`expression.ts:87` 用 `TYPOS.find(...)` 取**第一个**匹配，
所以一条气泡里同时含「已经」和「知道」时永远只错「已经」。影响很小，但可以在 ADR 里写明是有意为之。

### 2.6 `[动画表情]` 作为纯文本进了上下文

`chats/2306669773.jsonl:23,27`：

```json
{"role":"user","content":"[动画表情]"}
```

连续两轮里各出现一次。她对此没有反应（**这一点是对的**——她不该描述表情）。
但它作为一条独立 user 消息占据历史，且和后面的真消息并列（26+27 是「复活吧，我的爱人」+ 表情）。

**建议**：确认这是 `segmentsToText` 的有意行为（表情压成占位符）；若如此，考虑把连续的表情与相邻文本合并成一条，
避免她误判「他说了两句话」。

## 4. 修复优先级建议

| 序 | 改什么 | 为什么先做 | 验收判据 |
| --- | --- | --- | --- |
| 1 | 意图行加「先接话题」前置（1.1） | 直接对应他感觉到的「答非所问」；纯提示词/规则改动，零成本 | 构造「承诺未兑现 + 他发一句搭话」的场景，她先接搭话；模拟器可判 |
| 2 | 记忆写入按实体去重 + 召回按实体限流（1.2） | 打断正反馈环；改的是写入端，不动模型 | 新场景：同一实体连续 3 天都发生，召回里该实体 ≤2 条 |
| 3 | 「不再抽」改成可补抽 + `ENOTFOUND` 单独重试（2.2） | 她答应的事在丢；改了就不丢 | 断网模拟：抽取失败后，恢复时补抽成功 |
| 4 | 相机基金加迁移记录或改为事件推进（2.1） | 跨算法的数值跳变会变成可见矛盾 | 换算法当天，事件账里有对应记录 |
| 5 | 删掉 `[那里 → 哪里]`；ADR 0024 的比率数字改准（2.5） | 该词输出的是语义错误，不是错字 | 检查项：错词表里每条都是同音 |
| 6 | 空 `[Start a new Chat]` 不注入（2.3）；王者段按条目拆（2.4） | 清上下文死重，省预算 | 提示词里不再出现该宏 |

## 6. 本报告的方法与边界

- **只读分析**。没有改 `main`，没有改代码，没有重启任何进程。
- 所有结论都标了文件与行号；凡属推测的地方写明了「推测」。
- **DSH 侧没有 `runtime/bot`**，所以**复现不了线上行为**——本报告是静态推演 + 证据比对，
  不是实跑验证。凡建议里的「验收判据」都需要在你们那侧真跑。
