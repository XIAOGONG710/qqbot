# 1. 灵魂模块做得怎样

## 1.0 先说结论

**概念方向对、开销小，但实现是「一天做出来的原型」水平，不是可以长期无人值守跑的东西。** 约 1245 行生产代码（插件 708、生活引擎 172、常驻 179、工作桥 94、评分 70、工作模式 22），**自动化测试只有一个 16 行的、只覆盖 22 行 `work-mode.ts` 的测试**；核心（工具、评分闸门、账本、outbox、生活引擎、常驻进程、召回）零测试。我用**它自己的真实代码**复现了下面的缺陷（演示脚本把插件和生活引擎原样取出、用假上下文调用，全部重定向到临时目录，没碰真实数据）。

我的主观评分（只代表我的判断，不是测量）：概念 7/10；实现质量 3/10；安全与隔离 3/10；和仓库里已有系统的整合 2/10；可验证性 1/10。

## 1.1 做得好的

- **想法对路**：她自己决定记什么（`<<记住>>` / `<<日记>>`）、想查才查（`<<查：…>>`）、旧事实**软失效而不是删除**（PATCH `invalidated`）、30 天以上的事默认不主动塞、公开 / 私密日记分开、她能给自己加兴趣并放弃、能决定「离开电脑」。这些都贴着用户「像人一样独立自主」那句话。
- **生活引擎不调模型**（每 10 分钟推进一次状态，纯规则）：便宜、可预测，是个好选择。
- **常驻进程的工程底子不坏**：任务串行排队、超时、审计日志、离线状态、手动 wake / sleep 接口。
- **自己写明了已知缺口**（「情绪只有关键词级 appraisal」「STORY 是摘要拼接」「底账仍自动记」），没有夸大。
- 内部标记不进聊天历史、只有标记的气泡不发——这个坑（标记污染下一轮）它自己发现并修了。

## 1.2 实测复现的缺陷（真实代码，演示可重跑）

| # | 缺陷 | 复现结果 |
| --- | --- | --- |
| 1 | **`ledger_revise` 改错一条、而且不留痕。** 她看到的是账本**最后 12 条**（`ledger_read`），但 `revise` 的序号按**整个文件从头数**；还是原地覆盖、只有单槽 `.bak` | 账本 15 条时，她看到的第 3 条是「判断6」；她改「第 3 条」，被覆盖的是她从没看到过的「判断3」；原文随即不在文件里，下一次写入把唯一的 `.bak` 也换掉了。「改口也要留痕」只剩一个「（改口）」后缀 |

| 6 | **`outbox_send` 的消费端没有任何开关，绕过管道里所有的闸**（`app.ts:642-659`，每 30 秒把 `OUTBOX.jsonl` 每一行直接发到他的 QQ）：不过危机后 48 小时暂停普通主动消息（ADR 0068，红线第 4 条）、不过作息 / 夜间规则、不过出口检查、不过每日条数；**发出去的话不进聊天记录**，她下一轮不知道自己说过；读后清空文件，发送失败的行就丢了；「每轮最多一条」只写在工具说明里，代码没拦 | 读码确认（消费端只查 `dormancy?.isDormant()`，默认关） |

| 8 | **生活引擎编造了关于真人的事件**：写死的 NPC 里有「鸽鸽」（他的真实联系人），随机生成「鸽鸽发消息说周末可能约饭」「鸽鸽在群里吐槽老师拖堂」。用 `Math.random()`，不可重放，也不和仓库里已有的世界账（`world/`）对账——她可能把没发生的事讲给他、甚至讲给鸽鸽本人听 | 读码确认 |
| 9 | **两个「她现在在干嘛」的来源同时注入同一个提示词**：引擎的 `NOW.md`（「我在看书/追剧」，按它自己的作息）和仓库里原有的作息 / 状态行（上课、午休、起床时刻有抖动）。两边对不上时，她会前后矛盾 | 读码确认（`contact.ts` 同时拼两处） |
| 10 | 写死的绝对路径（`C:/Users/22601/…`、`D:/nodejs/…`）散在插件、桥、引擎、`app.ts`：放到别的机器上**静默失效**，不报错 | `git grep` |

## 1.3 设计层面的问题

1. **和仓库里已有的系统并行，而不是整合。** 几乎每个概念都有两套：拒绝（`herNo` ADR 0103 ↔ `REFUSALS.json` + 工作模式拒绝）、追求（`pursuits` ADR 0104 ↔ `INTERESTS.md`）、日记（`diary.ts` ↔ `JOURNAL.md`）、她的日子（`life/` + `world/` ↔ `her-life.mjs`）、设定与判断的账（`identity` / `ledger.ts` 哈希链 ↔ `SOUL.md` / `LEDGER.md`）。存放位置不同（一套在仓库的数据目录，一套在仓库外的 `~/.dsh/…`），语义不同，互不知道。用户的主渠道是 QQ，而 QQ 这一侧实际只拿到 `NOW.md`、评分、拒绝记录和 DSH 库召回——**灵魂的大部分在 DSH 桌面智能体里，QQ 上的她得到的主要是新增的风险。**
2. **「评分当闸门」把身份变化和讨好绑在了一起。** 她只有在他最近给的 👍😐👎 平均分够高时才能改自己的 SOUL；分低就禁止。这等于教她：想改变自己，先让他满意。和「不追参与度、不讨好」的项目底线反着。
3. **「私密日记」对他并不私密。** DPAPI 作用域是 `CurrentUser`、没有额外熵（`scripts/private-diary.ps1` 里 `Protect(..., $null, 'CurrentUser')`），**同一 Windows 用户下的任何进程都能解**——包括他自己跑那个脚本，也包括被注入的整机权限智能体；它能做到的是「不进提示词、不进聊天」，不是「他读不到」。如果要给她一个对他真的私密的地方，这不是它。（这点要诚实对用户说明，不要让「加密」两个字误导。）
4. **计划（10-27）里最关键的几条没有建出来，建出来的和计划的纪律相反。** 计划写的是：`kernel.json` 硬事实锁、`self/` 结构化账本、四个分层开关**默认全关**、先 dryRun、一次一个变量、上线用户在场。实际：没有硬事实锁；账本是仓库外的 Markdown；除 `selfDirectedMemory` 外**没有任何开关**，`recallWork`、`outbox` 消费端、「他最后说的是哪句」那一行、`NOW.md` 都是无条件开着；10-28 一天 36 个提交直接进了在跑的本机实例。
5. **「人设自完善计划」（10-28）想把性格、说话方式、边界从角色卡迁进可被她自己改写的 `SOUL.md`**（「SOUL 成为唯一人格来源」），闸门还是评分。**请不要做**：边界（承认自己是程序、危机、不接的话题）必须留在不可被模型改写的层里（角色卡 / 代码），否则一次注入就能改写它们；设定账本（ADR 0157）也应该把 SOUL 的每次改动算进去——用户原话是「核心人格设定原则上由你决定，必要安全维护也要说明并留痕」，现在 SOUL 在仓库外，账本管不到。
6. **成本没有上限也没有度量。** 每天 ≈4 次随机醒来 + 1 次睡眠整合，每次最长 5–10 分钟的智能体运行（整机权限、联网、多轮工具调用），没有预算、没有计量。

## 1.5 我建议的下一步（按顺序）

1. **先堵会伤人的：** ① `outbox` 消费端走和主动消息同一套闸（危机暂停、夜间、条数、出口检查）并写进聊天记录，放进开关；② `recallWork` 只对男朋友档、放开关；③ 生活引擎的负面判断只看「冲她的」（含「你」「别烦我」这类），倾诉不算；日期用 `herDay`；④ `sleepCheck` / `wakeCheck` 按她的作息；⑤ NPC 不要编造「鸽鸽」；⑥ `ledger_revise` 序号和展示对齐、改口追加而不是覆盖。
2. **补测试**：我复现用的那个假上下文装置可以直接当模板（插件的 `apply(ctx)` 只需要 `on` / `get` / `effect` 和 `tools.register`），一个下午能把每个工具、评分闸门、生活引擎、常驻接口都盖上。
3. **整合而不是并行**：定一个唯一的账（建议复用仓库里已有的 `ledger.ts` 哈希链和 `herNo` / `pursuits` / `diary`），DSH 桌面智能体通过同一份数据读写，而不是仓库外的 Markdown。
4. **不要做**「边界迁进 SOUL」；SOUL 的每次修改记进设定账本；评分闸门换成「频率限制 + 他确认」，别和满意度绑定。
5. 在以上做完之前，**我不建议给她更多无人值守的权限**（尤其醒来时的联网 + 整机权限 + 可自改提示词这个组合）。

# 2. 当前项目的缺点

先给规模，免得说空话：`packages/bot/src` 210 个文件 **4.08 万行**、测试 186 个文件 **3.18 万行**（2037 项）、**165 份 ADR（10-01 以来新增 166 份）**、`docs/` 230 个 md、**89 个开关**、26 天 **888 个提交**；最大的单文件 `platform/app.ts` 1986 行、`world/world.ts` 1570 行。

## 2.1 最大的五个

**① 没有可信的「是不是更像人了」的评估闭环——工程量远大于证据。**
- 真实使用量极小：线上聊天记录里，他 20 天（10-06 → 10-26）一共发了 **610 条**，前一周占一半以上且多数是在测试她；10-13 到 10-26 有好几天一天 ≤10 条（10-16 一条、10-18 零条）；同学档那位**总共 20 条**。整个「真实对话语料」是**一个人、约 600 条**。
- 评分者只有一个，而且是作者：知道所有内部机制，不是「不知情的人觉得像不像」。盲评用的评委模型本身不灵敏（我 10-22 量过：对「太完整太顺」几乎不敏感），只能靠自制的「检测器」和回放当代理指标；这些代理的效应量很小（例如开了尾词封顶后检测器 P(真人) 0.435 → 0.442）。
- 结果是：**3 周前后她到底有没有更像人，目前答不上来**。89 个开关里哪些真的起作用，也没有消融实验。
- 建议：先定 5–6 个固定指标 + 一套冻结的评测集；把「更多真实使用」当成第一优先级（让用户**知情的**朋友也能和她聊，群聊目前是 0 个群）；做一次消融（一次关掉一批开关，看指标掉不掉），删掉没用的。

**② 安全不变量靠管道，新增功能一个个开旁路。**
- 披露分级（ADR 0020）、承认自己是程序（ADR 0067）、危机最小规则（ADR 0068）、出口检查，都在「回复管道」里。10-24 之后加的功能一再绕过它：`outbox` 直发 QQ（绕过危机暂停和出口检查）、工作桥（模型输出直接回 QQ）、B 站私信分享（自己的 composer）、`recallWork` / `lifeLine`（把别人的内容注入别的联系人的提示词）、整机权限智能体 + 无人值守 + 可自改的系统提示词。
- 这不是某一个 bug，是**结构**问题：不变量没有一个「所有对外通道都必须经过」的单一关口。建议：把「发给任何人的任何文字」收口到一个出口函数（危机暂停 / 披露 / 出口检查 / 记入聊天记录），新通道只能调它；再加一条测试，扫描所有 `sendPrivateText` 调用点是否都经过它。

**③ 两套并行的「她」、两份分叉的数据、运行位置未定。**
- QQ 机器人（仓库内）和 DSH 桌面人格（仓库外的 `~/.dsh/…`）几乎每个概念各做一套（1.3 第 1 点）。
- 她 10-27 起跑在 DSH 本机：本机数据目录 `runtime/bot-shadow` 只有补回的 36 条聊天 + 之后的新状态；VM 上有原来的全部（约 53 MB 的 `runtime/bot` + 1.5 GB 的 Hindsight 长期记忆），**两份已经分叉且不能简单合并**（日记、记忆要单独设计迁移）。「唯一权威源」没定。
- 本机没有服务守卫、心跳、断网通知；VM 是停着的；任何一边都不是完整的生产环境。

**④ 自动化安全网实际上是关着的，而且没人知道。**
- **GitHub CI 自 10-20 01:00 起一次都没真正跑过**：每个 job 都是「*The job was not started because recent account payments have failed or your spending limit needs to be increased*」（账单 / 额度），近 300 次里 215 次失败、30 次取消，最近一次成功是 10-20。此后 `main` + `dsh/qq-control` 上的 **197 个提交**（我的推送也在内）都没有自动回归。（原因很可能是 `windows-latest`（私有仓库按 2 倍计费）+ `push: branches: ['**']`——每条分支每次推送都跑一遍，888 个提交把额度耗光；这是推断。）**这得用户去 GitHub 的 Billing 里处理**，我这边做不了。
- 即便 CI 开着，2037 项测试也有结构性盲区：**重构后设定账本 34→0 它们看不见**（测试都显式传路径）、灵魂 / 常驻 / 工作桥 / 生活引擎零测试、脚本和运维（服务守卫、启动脚本）没有测试、多进程行为没有测试。「测试全绿」在这个项目里反复**不等于**能用（10-09 NapCat 内存满、10-11 整体被杀、这次的重构回归）。
- 红线靠自觉：「线上目录只读」「一次一个变量」「上线用户在场」「推送前跑全量」在 10-24 之后被一批批大改动稀释（本机一次性补上 VM 上那一大批开关、一天 36 个提交、红测试推了出去）。

**⑤ 体量失控：开关、ADR、文档、单文件，已经没有人能完整说出「现在到底是什么行为」。**
- 89 个开关（`features.ts` 登记的）；线上 `koishi.yml` 里 72 个标量开关、**59 个开着**；开关之间的组合从未整体测过；每个开关都有各自的回放 / 单测，但没有「全开」的整体行为验证。
- ADR 一天 6 份，很多是对上一份的「补记 / 调整」，ADR 退化成了变更日志，真正的决策被淹掉；BOARD（唯一总表）10-22 以后停更，我 10-26 才补；交接没推送就让对方「断片」；`exchange/` 里 130 个证据文件、88 个交接、59 份研究。
- `app.ts` 近 2000 行、`contact.ts` 近 1000 行；10-27 的「12 模块」重构只改了目录，**模块之间没有接口边界**（互相随便 import），所以挪文件才会改 66 处引用、才会踩到路径回归。
- 每轮提示词一路叠加（意图行、形状行、记忆块、`lifeLine`、`lastUserLine`、工作模式行、评分行、拒绝行……）；DSH 自己的审计就列了 6 个可调点。叠得越多，互相矛盾的指令越多——「太顺」「AI 味」迟迟下不去与此有关（这是推断，没有消融数据）。

## 2.2 其他缺点（次要，但真实）

- **运维单点**：VM 只有 6 GB 内存、空闲常 0.8–1.7 GB（一次浏览器会话就要 ~450 MB）；上游网络多次断（10-18 约 17.5 小时、10-26 约 30 分钟）；NapCat 是非官方 QQ 协议（封号风险由用户承担）；DeepSeek 单一模型供应商；Hindsight 的 1.5 GB 长期记忆**只有一份、没有机外备份**（文本导出 / 备份 10-22 被暂缓）。
- **用户单一且是开发者**：「像不像人」「太不太顺」都由作者判断；她的「生活」是模拟出来的（作息、NPC、事件），一旦被问到细节就靠一整套事实核对 / 账本补；没有真实世界的锚（照片、语音、群、见面——都还没有）。
- **真人的数据**：名单里的朋友是真人，他们的话被存、被总结进记忆、现在还可能被注入别人的提示词；用户说「他们都知道这是 bot」，但「知道她是 bot」不等于同意被记录 / 被转述。《人工智能拟人化互动服务管理暂行办法》适用与否我没有逐字核对（ADR 0067 / 0147 里标了），平台条款（QQ 非官方协议、B 站自动化账号）也是风险。
- **成本没度量**：每轮模型调用数（回复 + 重写 + 出口检查 + 内心 + 事实核对 + 看图 + 深思）、延迟、费用都没有统计，也没有上限。
- **知识靠转录和记忆文件，不靠仓库**：这轮对话的上下文（以及我这边的记忆索引已经 40 多条）只有当前会话看得到；我的额度快用完，新会话要读一大堆才能接上。人换了，信息就断。唯一的人类把关者是用户一个人。
- **三个 AI 改同一个仓库、协调靠文件**：线上目录曾被别的窗口的未提交改动污染（10-10、10-11），这次又出现「VM 仍跑 6169551」这种和现实不符的交接。
