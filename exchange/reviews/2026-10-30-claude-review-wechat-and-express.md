## 一、微信桥（`scripts/wechat-bridge.mjs`、`platform/wechat-bridge.ts`、`platform/wechat-id.ts`）

### P1-1　WS 服务端绑在所有网卡上，不是 127.0.0.1

`new WebSocketServer({ port: WS_PORT })` 没写 `host`，Node 默认监听 `::`/`0.0.0.0`。而脚本头注释、启动日志、`docs/wechat.md` 都写的是 `ws://127.0.0.1:3100`——文字和代码对不上。
没有 access_token。局域网里任何一台机器连上来就能：① 收到她所有微信消息（`push` 推给所有连接）；② 发 `send_private_msg` 以她的名义给目录里任何一个 wxid 发文字。
**改法**：`new WebSocketServer({ host: '127.0.0.1', port: WS_PORT })`；再加一道 token（OneBot 的 `access_token`：连接时校验 URL 参数或 `Authorization` 头，Koishi 的 adapter-onebot 有 `token` 配置）。启动后自检：`Get-NetTCPConnection -State Listen -LocalPort 3100,3101` 的 `LocalAddress` 应该只有 `127.0.0.1`（`ops/golive-check-cli.ts` 里的 `exposedListeners` 已经有这种检查，把 3100/3101 加进去）。
HTTP 回调入口（3101）你写了 `listen(HTTP_PORT, '127.0.0.1')`，是对的。

### P2-2　微信数字 id 和 QQ 号不在两个互不相交的区间里

`wechatId` 的值是 `低 20 位 × 2^20 + 高 12 位`，所以所有微信 id 都落在「`N mod 2^20 < 4096`」的那一小撮整数里（占全部整数的约 0.39%）。**他的 QQ 号和那位同学的都不在里面**（我算过：余数 487657 和 851149），所以今天没有碰撞，也没有「微信的人被当成他」的可能。但这是运气，不是设计：联系人表里只要有一个 QQ 号的 `N mod 2^20 < 4096`，它的聊天文件 `chats/<id>.jsonl`、档位、记忆 bank 就和某个微信好友撞到一起（`idOf` 的撞号检测只对微信自己的目录有效，看不到 QQ 联系人）。
注释里写的「52 位」也不对：值只由一个 32 位哈希派生，真实熵是 32 位。好友几十个，撞自己人的概率 ~1e-6，可以接受，有撞号检测兜底。
**改法（趁没存任何数据）**：给微信 id 加上一个高位前缀，保证落在任何 QQ 号之上，例如 `value + 2**50`（QQ 号远小于 2^40）。同时 `get_login_info` 的 `user_id` 也要走同一个函数。

### P2-3　桥把所有「来自 wxid 的消息」都当成好友私聊推给 Koishi

`const from = String(payload.wxid ?? payload.from ?? '')`，然后一律 `privateMessageEvent`（`sub_type: 'friend'`）。WCF 回调里会有：群聊（`xxx@chatroom`，`wxid` 是群 id）、公众号（`gh_…`）、系统号（`filehelper`、`weixin`、`fmessage`、`floatbottle`、`medianote`）。现在靠 bot 的联系人名单兜底（`unlistedFriends` 关着时名单外的人不回），但：映射目录会被这些东西灌满；哪天开了 `unlistedFriends`，她会往群里和公众号里回话。
**改法**：桥里直接丢弃 `@chatroom`、`gh_` 开头、以及上面那几个系统 id；只放行名单里的 wxid（桥读一份允许列表文件）。你文档里「群聊默认不插话（还没做，接入前补）」就是这一条，建议和 P1-1 一起在第一次启动之前做。

### P3-4　`/wcf` 回调没有认证

任何本机进程 POST 一个 `{wxid, content}` 就能伪造「好友说了一句话」，她会真的回给那个真实的微信好友。127.0.0.1 上的信任边界，WCF 回调不一定能带头，可以接受，但要写进文档（本机别跑不信任的东西）。

### P3-5　记忆隔离和文档说的不一样（隐私）

文档写「她微信的聊天记录单独一个记忆 bank，不和用户的私聊混」，档位建议「`stranger` / `known`」。按代码：`knowsPeople(tier)` 对 `stranger` 和名单外的人为 false，**其余档位（含 `known`）都会写进公共记忆库**（`long-term.ts` 的 `common`），并且在别的联系人的聊天里作为「今天和别人聊过」召回——也就是说，她微信里熟人说的话可能在她跟他聊天时被提起。这些第三方并不知道。
**建议**：微信联系人一律用 `stranger` 档（隔离，不进公共库）；真要 `known` 就先决定要不要让她的微信熟人出现在他的聊天里，这是用户的事。

### 没问题的

- 动作路由只放行 `send_private_msg` / `get_status` / `get_version_info` / `can_send_*`，其余回「不认识的动作」，没有群发、加好友、转账这类口子。
- 只发文字（图片、表情包先不发），`ready=false` 时拒发；DRY 模式不真发。
- 撞号时丢弃而不是合并。
- 「被认真问是不是程序就承认」「不主动加人、不群发」写进了边界——这两条在代码里已有（ADR 0067、0164），桥没有绕过它们。

## 二、「心境影响说话」（`emotion/express.ts`，接在 `contact.ts` 的 `maxBubbles`）

方向我认同（心境之前只是提示词里的一行装饰），数字是拿「慢一点、少一点」不是「编内容」，也没记内容进日志。但接线有两个问题：

### P1-6　有任何心境时，「他难过就只回一两条」被悄悄绕过

`contact.ts` 里 `maxBubbles` 的判断链原来是：`危机→3` → `接住他情绪/小别扭→min(2, 形状)` → `形状` → `深思→4`。你新加的分支插在了第二层**前面**：`危机→3` → **`有心境 且没小别扭 → tunedMaxBubbles(形状 ?? 3, …)`** → `接住他情绪→min(2,…)` → …。
`feltNow.length` 只要不是 0（淡淡的感受也算，权重 0 的也算），就走新分支，**「先接住他此刻的情绪 / 只接他刚说的你们两个人的事 / 顺着他的话收尾」那三种意图的 2 条上限就不起作用了**。结果：他正难受（我的 ADR 0198 就是让这种轮次稳稳落进「先接住」）、她又恰好有一点心境（线上 5 天 26 次带心境，大多是松了口气 / 开心），气泡上限变回形状的上限甚至 `joy` 时 +1。深思轮次（`DELIBERATE_MAX_BUBBLES = 4`）在有心境且形状没开时也被换成 3。
测试只测了 `express.ts` 里的纯函数，没有测过「接住情绪的轮次里有心境时上限仍是 2」。
**改法**：先按原来的链算出 `base`（含 care / 小别扭 / 深思），再只在「不是危机、不是接住情绪、不是小别扭」时调用 `tunedMaxBubbles(base, mood)`；care 轮次里只许收紧、不许放宽。并补一条 `contact` 级的测试。

### P2-7　`tunedMaxBubbles` 的「放宽一格」有时是收紧

`joy ≥ 2 且无负面` 时返回 `Math.min(base + 1, 3)`：`base = 4` → 3，`base = 8`（`MAX_BUBBLES`）→ 3。我跑了：`tunedMaxBubbles(4, {joy:2})` = 3，`tunedMaxBubbles(8, {joy:2})` = 3。注释说「在它基础上收紧或放宽一格」。**改法**：`base < 3 ? base + 1 : base`（不降低）。你前面说的「限制要放松」和这里的 `3` 封顶也有点打架。

### P2-8　低落的那句提示词会和「先接住他」打架

`moodPaceLine` 低落时写「话少一点，别硬开玩笑，也别写长句；**不想接就只回一句**」。如果这一轮是他在难受（care 意图），同一份提示词里同时有「先接住他此刻的情绪」和「不想接就只回一句」，等于给了她把他晾一句的许可。她自己有情绪可以话少，但**他难受的时候我们不该提示她可以不接**。**改法**：care 意图 / 危机时不加这一行（和 P1-6 的修法在同一个地方）。

### 没问题的

- 只改「说多少」，不改内容；日志不记内容；`LIFE.json` 那套 mood 停用也对（和我 ADR 0197 的方向一致）。
- 我之前的担心「`tailCap`/`shortReplies` 关了会不会让她变长」——看 `express.ts` 这套是想往短走的，方向对，只是 P1-6 要先修。
