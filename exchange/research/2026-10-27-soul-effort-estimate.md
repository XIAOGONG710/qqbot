# 把现在的她改成「有灵魂」：工程量、难点、改完什么样

日期：2026-10-27 · 基于项目评估（2,030/2,034 测试、28 提交未合、自主层缺失）

## 一、先给结论

- **MVP（能明显感觉到“她有自己的时间、有没给你看的日记、有偏好”）**：约 **12–15 个开发日**（单人、含测试），3 周内可见；
- **完整版（加判断清单、拒绝反省、反馈闭环、观察台、评估体系）**：约 **31–41 个开发日**，全职 1.5–2 个月；
- **不是“改一段提示词”**：动的是数据模型 + 三个循环 + 表达管线 + 评估方法，**核心代码新增约 5–8k 行、改动 2–3k 行**，新增 ADR 8–12 份；
- **改完不会变成人**：会有“有来历、会拒绝、有自己时间”的行为；仍会 OOC、会矛盾、会忘事——这是 LLM 的边界，不是工程能消除的。

## 三、难点（按真实难度排序）

1. **怎么证明“有灵魂”**（最难）
   没有 ground truth。“更像人”是主观判断；只能做 A/B 盲评 + 行为指标（卡外率、主动、拒绝、跨天一致）。评估体系本身要 3–4 天，而且会被质疑。

2. **一致性与叙事漂移**
   事件 → 判断 → 表达三层容易各自为政：她今天说喜欢 A，明天事件里写 B，回顾又编一个 C。dsh-fish 的解法是回顾必须带事件 id、允许“我没想清楚”；我们要抄的是这个纪律，不是抄文案。

3. **和现有管线打架**
   - 6000 字角色卡是常量，新“判断”必须**盖在卡上而不是替换卡**；
   - `shape.ts`/`lengthHint` 每轮注入、`fact-check: fix` 会改写卡外说法——不改这两处，自由时间与偏好都会被压回去；
   - `proactive-planner` 的动机是模板，接反馈闭环要改它的调度条件，容易牵一发动全身。

4. **记忆质量**
   抽取会错、会重复、会漏；私人日记可能写出尴尬/重复/不合适的内容。需要去重、长度上限、敏感内容过滤、可删除。

5. **成本与时延**
   事件抽取（每段对话 1 次）、自由时间活动（每天 3–5 次）、周回顾（1 次/周）、记忆压缩。估算 **API 成本 +20–40%**，回复时延 +200–500ms（记忆分级召回）。dsh-fish 一个月 13 亿 token 是极端值，我们按小流量起步。

6. **自由时间的安全边界**
   她能自己“玩”，就要定义“能玩什么/不能做什么”：只读 B 站、不发公开内容、不花钱、不碰设备控制；否则自由会变成事故（鱼灾/资料泄露）。

7. **数据迁移与双实例**
   VM 一份、本机一份、Hindsight 两库；先定唯一权威源，再谈迁移；聊天记录能拷，记忆/日记不能简单合并。

8. **LLM 的能力边界**
   她会“看起来有想法”，但底层仍是下一 token 预测；遇到强诱导会露馅，遇到复杂情境会自相矛盾。工程能做的是**让她有稳定的来历与边界**，不是让她真的“想”。

## 四、改完之后，表现会怎样（诚实预期）

### 第 1 周（MVP 上线）
- 她会**自己开摆**（“今天不想看”），日记出现**私人版**（不给你看）；
- 偶尔会提“上次那件事”（如果事件流接上）；可能变得话少、更任性；
- 你会第一次觉得“她有没告诉我的事”。

### 第 2–4 周（判断/拒绝/反馈接上）
- 有 **≤12 条偏好清单**，问“你喜欢什么”会给卡外答案；
- 会**拒绝**，拒绝后有反省记录；你长期不回，她会**减少分享**；
- 周回顾能说“我最近变了”，且能指到具体事件。

### 不会发生的事
- 不会真的“有意识”；不会永远自洽；会 OOC、会忘、会重复；
- 不会替你写作业/投稿（内容生产另算）；
- 不会免费：成本 +20–40%，且需要你持续给反馈（她看你反应）。

### 失败模式（要提前接受）
- 私人日记写得尴尬/重复 → 需要过滤与长度限制；
- 过度拒绝/变冷淡 → 需要“拒绝预算”（比如一周最多 2 次硬拒绝）；
- 卡外偏好与硬事实冲突（生日/家庭/学校）→ 硬事实护栏；
- 评估争议（“这不就是随机发挥”）→ 用跨天一致性指标说话。

## 五、验收指标（改完必须能测）

| 指标 | 目标 |
| --- | --- |
| 卡外偏好率 | >0，3 天后可召回 |
| 自主发起 | ≥3 次/周 |
| 真实拒绝 | ≥1 次/两周，有反省记录 |
| 跨天一致性 | 同一偏好 3 天后不矛盾 |
| 鱼八股率 | <5% |
| 自由时间使用 | 每周 ≥5 次无目的活动 |
| 成本 | 增幅 ≤40% |
| 回归 | 2,034 测试全绿 |

## 六、建议节奏

1. **W0 先做**（2–3 天）：测试全绿、备份、告警、合并；没有这个基线，后面所有“她变了”都无法判断是她的变化还是 bug；
2. **MVP 12–15 天**：W1+W2 简化+W3+W9 三指标；
3. **观察 2 周**：看她是否真的“有自己时间/有私人日记/有卡外偏好”，再决定是否做 W5/W6（判断与拒绝）；
4. **完整版再 2–3 周**。

一句话：**工程量是“一个中等功能模块”的量级（3 周 MVP / 6–8 周完整），难点不在写代码，在评估、一致性和与现有卡/形状管线的冲突。**
