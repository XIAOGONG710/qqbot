# 同类项目对比与可化用方案

更新时间：2026-11-03

这份记录用于指导 `qqbot` 的后续取舍。目标是吸收已经验证过的交互和工程做法，不把项目改造成另一个框架。

## 项目定位

当前项目已经形成了清晰的分层：

| 层 | 当前职责 |
| --- | --- |
| Koishi | 配置、控制台、插件生命周期、状态展示 |
| NapCat / OneBot | QQ 登录、收发消息、QQ 原生动作 |
| bot | 人设、作息、关系、真人式数值、主动消息、现实世界数据 |
| Hindsight | 长期记忆的写入与召回 |
| DSH | 显式调用的外部思考协作者 |
| 手机伴侣 | 受配对、白名单、确认和审计约束的移动端通道 |

这个分层应当继续保持。新增能力优先放入现有层，避免再造一个平行的机器人核心。

## 对比结果

### Koishi：模块化和控制台入口

Koishi 官方把插件作为主要扩展单元，并通过控制台和市场管理插件。适合吸收的优点是“功能以模块呈现、配置集中管理、开关状态可见”。

我们已经有 `platform/features.ts` 的功能总表和自定义中文状态页，下一步只应继续补充：

- 每个能力的中文说明、依赖关系和关闭后的影响；
- 配置页与状态页使用同一份能力定义；
- 低风险能力允许热更新，涉及连接和安全边界的能力要求重启或明确确认。

不建议再引入一套独立插件运行时，否则会出现 Koishi 插件、QQ 插件、手机插件三套生命周期互相不一致的问题。

### SillyTavern：扩展面板、角色资料和记忆工具

SillyTavern 把扩展集中到一个可启用 / 停用的面板，并把角色卡、World Info、自动摘要、向量检索和数据资料库分开管理。这个思路适合用于“能力可发现”和“记忆来源可解释”。

可化用：

1. 控制台按“她是谁、她的世界、日程、相处方式、记忆与安全、工具”组织，而不是按代码目录组织；
2. 长期记忆继续保持“写入、召回、关系概况”三种用途，状态页只展示健康、时间和数量，不直接暴露聊天原文；
3. 后续可以增加一个手动的“记忆检查”入口：只允许查看、删除和重新整理已授权的记忆，不允许通过网页任意改写事实；
4. 若未来接入向量检索，必须作为可关闭的召回增强层，并保留当前 Hindsight 的时间衰减、重要性和证据审计。

不直接照搬：SillyTavern 的向量化会增加索引、模型和缓存的一致性成本；当前 Hindsight 记忆已经包含按联系人 / 档位隔离、共同记忆、淡化和证据规则，先不要并行维护第二套记忆库。

### Open WebUI：能力声明和工具边界

Open WebUI 将记忆、知识库、网页搜索、代码解释器、通知等能力作为模型可以调用的工具类别，并强调工具可发现、可配置和按模型启用。

可化用：

- 继续维护统一的能力清单，而不是在 QQ、DSH、手机端各写一份动作说明；
- 给每个工具标明“自动执行 / 需要确认 / 可撤回”；
- 让状态页展示能力类别和当前开关，执行细节进入审计记录；
- 现实世界数据统一走 `world` / `platform/web`，在回复中保留来源摘要和失败状态。

不引入“Open Terminal”式的全权限执行。项目已有设备动作白名单、确认、熔断和审计，这条边界必须继续保留。

### NapCat：通道与插件边界

NapCat 官方将插件机制、OneBot 事件和 QQ 原生动作分开，并提供插件模板与热重载能力。适合我们的做法是把 NapCat 当作可靠的 QQ 传输层，行为决策继续留在 bot，不在 NapCat 插件里复制人格、记忆和作息逻辑。

这样可以避免 QQ 重连、手机伴侣连接和 DSH 连接各自维护一套上下文。

### YuKiKo、Yuki 和 personagent：多渠道连续性与证据化

这些项目的共同优点是：多平台接入、长期记忆、插件化工具、主动参与可选择开启，以及对事实或动作保留审计记录。

我们已经具备对应的基础：

- QQ 与手机伴侣复用同一 DSH 语气和状态摘要；
- Hindsight 记忆按联系人 / 档位隔离；
- 设备动作有白名单、确认和审计；
- 记忆账本、时间线和身份账本可以追溯变化。

下一步适合补的是“可观察性”，而不是迁移到 Python 或重写 WebUI：在控制台为记忆、DSH、手机伴侣和现实世界数据提供统一的最近一次成功 / 失败、重试原因和关闭入口。

### DSH QQ Bridge：显式双向同步

现有 DSH 连接已经采用更稳妥的方式：QQ 中明确发起 `/dsh` 才把最近几轮带入外部咨询，状态经过脱敏，回答再用她的中文语气返回。类似桥接项目证明双向同步很实用，但也说明同步必须有明确入口，不能把所有 QQ 原文自动转发到外部模型。

## 采用优先级

| 优先级 | 方案 | 适配方式 | 风险 |
| --- | --- | --- | --- |
| 已完成 | 中文状态页与能力分组 | 复用 `features.ts` 和 Koishi 自定义页面 | 低 |
| 已完成 | DSH / QQ / 手机伴侣统一语气与状态 | 复用 `dsh-link.ts` 和 companion runtime | 中 |
| 已完成 | 动作确认、白名单、审计 | 继续复用 `device-actions.ts`、`action-policy.ts` | 低 |
| 下一步 | 统一能力说明和依赖提示 | 由功能总表生成配置页与状态页说明 | 低 |
| 下一步 | 记忆检查入口 | 只读、删除、重新整理，全部写审计 | 中 |
| 下一步 | 现实世界数据来源摘要 | 每项数据保留来源、时间和失败原因的中文摘要 | 中 |
| 暂缓 | 向量记忆第二实现 | 先验证 Hindsight 不足再评估 | 高 |
| 不采用 | 电脑最高权限 / 任意终端 | 与现有白名单和确认边界冲突 | 极高 |

## 设计约束

1. 新能力必须先进入能力总表，再接入 QQ、控制台或手机端。
2. 任何外部服务都要有开关、超时、失败降级和最近状态。
3. 任何能改变设备、账号或外部数据的动作都必须经过白名单、确认和审计。
4. 记忆写入必须可追溯、可删除，不能用摘要覆盖原始事实而不留记录。
5. 控制台默认只展示中文状态；提交号、内部键名、原始错误和协议字段进入诊断层。
