# 可行性分析（2026-10-07）

结论先给：**技术可行（高）、资源可行（中）、流程是真正的瓶颈（中）**。
唯一会卡住的不是新功能本身，而是**验证方式**和**串行化的机器**。

---

## 一、技术可行性：高，但有一个架构陷阱

### 1.1 `world.ts` 是什么

`packages/bot/src/world.ts` 不是状态机，是**确定性纯函数重放**：

```
simulateWorld(world, schedule, until)   // world.ts:101
  for (day = world.startDay; day <= until; day += 1) { ... }
```

- 从 `startDay` 一天一天推到「今天」，每天算出：天气、猫喂没喂、快递到没到、作业、相机基金、和家里视频、小事。
- 所有随机来自 `unit()`（`world.ts:418`，FNV-1a）——**输入是「日期 + 名目」的字符串哈希**。
- 所以：**同一天对所有人一样、重启一样、重放一样、模拟器能重放、不存随机状态。**

这套设计的价值很高，别推翻它。

### 1.2 陷阱：世界不可被改变

因为结果是重放出来的，**她的行为没有入口**。这带来三个直接后果：

| 后果 | 表现 |
| --- | --- |
| 言行不一致 | 说了「我去喂土豆了」，`worldAt()` 里土豆还是没喂 |
| 事件无生命 | 事件出了就一直在，没有「发生 → 挂着 → 沉淀」 |
| 没有意外 | `chance` 是均匀哈希，没有尾部事件，没有连锁 |

这正是 W3 缺失的根因，也是为什么 **W3 不是「加个 tick」**。

### 1.3 解法：重放 + 覆写（overlay）

```
runtime/<dataDir>/world/
  state.json        ← worldLogger 现在就在写（world.ts:336）
  overrides.json    ← 新增：append-only，她声称做过的事
```

```
worldAt() = simulateWorld(..., 今天) ⊕ overrides[今天]
```

四条纪律：覆写只增不减（保住可重放）、每条带来源（可审计）、冲突时以覆写为准并记日志、
抽取只认**明确声称**（不从语气推断）。

**为什么这可行**：

- 落盘原语现成——`packages/bot/src/json-file.ts` 的 `writeJsonAtomic` / `readJsonOr`。
- 抽取通道现成——`promises.ts:209 promiseKeeper()` 已经在每段聊天结束后抽一次，
  由 `app.ts:233 syncMemory()` 每 5 分钟驱动。**加一类抽取，不加一次调用。**
- `describeWorld()`（`world.ts:252`）吃的是 `WorldNow`，**上游改了它不用动**。

**风险很低**：最坏情况是「她说了但没记上」，那走正常衰减，不会产生矛盾。

## 二、资源可行性：中（内存是硬约束）

### 2.1 实测

| 项 | 数值 |
| --- | --- |
| CPU | Intel i7-14650HX，16 核 / 24 线程 |
| 内存 | 总 15.7 GB，**空闲 6.3 GB** |
| 磁盘 | C: 剩 141 GB |
| Node | `node -v` → **v26.4.0**（`CLAUDE.md` 记的是 v24.21.0，需核对） |

### 2.2 已经吃过一次亏

10-07 **18:17、19:51 两次「out of memory」**，Postgres 崩溃后 2–3 秒自动恢复，
都发生在 **3 次并行的带记忆模拟器**批次里。线上 6 个库都在，两次线上 bot 都空闲、日志没有失败。
`530ccaa` 已改成「带记忆的场景默认一次只跑一个（`--parallel N` 可改）」。

### 2.3 新增子系统吃不吃内存

| 子系统 | 形态 | 内存增量 |
| --- | --- | --- |
| 0027 世界回写 | 纯计算 + 一个 JSON | ~0 |
| 0028 挂心的事 | 纯计算 + 一个 JSON | ~0 |
| 0029 情绪惯性 | 纯计算 + 一个 JSON | ~0 |
| 0030 关系温度 | 一个 JSON | ~0 |
| 0031 意外与连锁 | 纯计算 | ~0 |
| 0032 媒介层 | 一个 HTTP 调用 + 当天缓存 | ~0 |

**结论**：新增功能几乎不吃内存。真正吃内存的是**验证方式**（并行模拟器）和
**常驻服务**（Koishi + NapCat + Postgres + onnxruntime 嵌入模型约 2.2 GB）。
所以纪律比优化重要：**带记忆串行、回归分批**。

## 三、上下文可行性：够用，但要守预算

- 现配置：`maxContext 16384`、`maxTokens 4096`（开思考）。
- 10-04 实测：`maxContext 8192` 时「为了记忆挤掉正在聊的内容」，改成 16384 后 19:53 那条提示词
  放下了 185 条消息 / 153 条聊天记录。
- 现在提示词里已经有：档位角色卡（男朋友档约 1,960 token）、示例 9 段、聊天记录、召回
  （`MAX_RECALLED 12` / `RECALL_TOKENS 1000`）、时间块、世界块「你那边」、末尾指令。

**新增项都是「一行事实」**：

| 新增 | 估计 |
| --- | --- |
| 情绪多维（最突出的 1–2 维） | ~30 token |
| 关系温度（对当前这个人一行） | ~40 token |
| 挂心的事（只放最紧迫 1–2 条） | ~60 token |
| 媒介（今天刷到什么，1 条） | ~40 token |
| **合计** | **~170 token** |

**结论：装得下。** 但要守两条：
① 它们合成**一个「今天这一层」区块**，不各开一段；
② 定一个上限（建议 ≤600 token），超了先砍媒介、再砍挂心的事。

## 四、流程可行性：中——这才是瓶颈

每个功能现在都要走完整条链：

```
取证 → ADR → 用户确认 → 小步提交 → 真模型模拟器批次（各 3 次）→ 上线 → 打码查日志
```

**成本不在写代码，在跑批次**：

| 项 | 规模 |
| --- | --- |
| 模拟器场景 | 46 个（`packages/bot/sim/`） |
| 单项回归例（`classmate-probes`） | 1,185 项检查 |
| 全量测试 | bot 393 / character-tools 32 / 插件 23 |
| 10-07 那批综合回归 | 8 个场景各 3 次，其中一个 shell 因内存不足被停 |

**对策**：

1. 每个 ADR 只跑**受影响的场景 + 一张跨天链**。
2. 全量回归攒到**批次末**跑一次。
3. 抽取通道**复用不新增**（0027/0028 挂在 `promiseKeeper` 那一批上）。
4. 真模型批次**一次只跑一个**带记忆的场景。

## 六、总体判断

| 维度 | 判断 | 一句话 |
| --- | --- | --- |
| 技术 | **高** | 全是本地纯计算 + 现成的落盘与抽取通道；唯一要设计的是覆写层 |
| 资源 | **中** | 新功能不吃内存；吃内存的是验证，纪律已经立了一半 |
| 流程 | **中** | 真模型批次的时间是真成本，靠「少跑、跑准、攒着跑全量」压低 |
| 依赖 | **两处要人定** | 决策 1（情绪跨天）和决策 2（不完全配合），都是 ADR 级别的岔路 |
| 结论 | **可以按批次 1 → 2 → 3 推进** | 批次 1 与任何裁决无关，可以立刻开始 |
