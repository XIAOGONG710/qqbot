# ADR 0142：她对 QQ 账号的控制面（默认关，按后果分档）

- 状态：**已实现，未上线、未在真 QQ 上验证**（分支 `dsh/qq-control`；`qqControl` / `qzoneBrowse` 两个开关，默认 `off`）
- 日期：2026-10-25
- 关联：[ADR 0083](0083-presence.md)（她的签名、说说，「空友爱看」）、[ADR 0085](0085-napcat-probe.md)（同样用只读探针先问「这台 NapCat 有什么」）、[ADR 0079](0079-poke.md)、[ADR 0089](0089-bilibili-account.md)（B 站号的开关分层）
- 用户授权：2026-10-25「让她完全控制自己的 QQ 账号，风险由我实名承担，最好能让她自己翻看 QQ 空间的空友爱看」。实现与测试；上线（开开关、重启）仍要用户当次点头，一次一个开关。

## 背景

NapCat 给了约两百个动作：发消息只是其中一小块，账号本身还有资料、头像、好友申请、群管理、空间；而她现在的「账号」除了收发消息，其余全是机器人默认值（见 ADR 0083）。用户要的是「这个号就是她的」，并且点名要她自己翻空间里那种混着陌生人的「空友爱看」流。

直接全放开的代价不是技术问题：任何一个 bug 都会以「她动了真人」的形式出现——加错人、踢错群、群发、改头像、发一条所有人都看得到的说说。这个号是真实身份，封一次就没了。

## 决策

### 1. 控制面是一个「白名单 + 分档闸」，不是把 NapCat 全部暴露给她

`packages/bot/src/account.ts`：登记过的动作才可能执行，查不到的（哪怕 NapCat 有）一律拒绝。四档：

| 档 | 例 | 开 `qqControl` 的哪一档才放行 |
| --- | --- | --- |
| `read` | 读好友 / 群 / 空间 / 聊天记录 | `read` 就放行（只读不写） |
| `profile` | 改签名、昵称、头像、群名片 | `on` |
| `social` | 好友申请、发私聊 / 群消息、群公告、点赞、说说、撤回、已读、在线状态 | `on` |
| `dangerous` | 删好友、踢人、禁言、全员禁言、设管理员、退群、建群 | `on` **且** `qqDangerous: true` |

写动作还要同时满足两条：

- **允许清单**：`qqAllowFriends` / `qqAllowGroups`（空 = 一个都不许）。名单外的好友和群，写动作直接拒绝；
- **限流**：一小时最多 `perHour` 次（默认 6）。读不算。

每次动作都写审计（`audit` 回调由调用方接）：时间、动作、对象、放没放行、拒绝原因或错误信息；**不写正文**。内存里保留最近 200 条，落盘由调用方决定（线上接到 `runtime/bot/account-audit.jsonl`）。

### 2. 她自己翻空间动态（`qzoneBrowse`）

空间没有对外接口（ADR 0083 已确认投稿要客户端点按钮），能读的只有 NapCat 的扩展动作，而动作名各版本不同。`packages/bot/src/qzone-feed.ts`：

- 按候选名逐个试（`get_qzone_msg_list` / `get_qzone_feeds` / `qzone_get_feeds` / `get_qzone_recent`），**哪个能用记下来**；全不通返回 `undefined`，上层只记一行「这台 NapCat 读不了空间」，不假装看到；
- 读回的东西归一成「一条说说」：id、正文、图数、时间、赞和评论数；认不出正文的（只有图）跳过；
- 摘成一句话进提示词：`你刚才翻了会儿 QQ 空间，刷到：「…」「…」（这一页一共 N 条）`，**只留文字**，别人的名字、图、链接都不进提示词；
- 节奏：`09:00–23:00`、醒着、两次之间至少 2.5 小时；睡着、上课不翻；读到的这一句 6 小时内有效（`describeSelf` 一起给她，和签名、说说同一行）；
- `dryRun` 只写 `presence/drafts.md`，不进提示词；失败只记一次日志。

**没有做**：点赞和评论空间动态。动作名（`like_qzone_msg` / `comment_qzone_msg`）没法在这台机器上验证，而且一旦错了是公开动作；等探针在线上确认了再单独接（`social` 档，默认关）。

### 3. 好友申请、群管理、资料——能力都有，开关都在

`set_friend_add_request` / `set_group_add_request` / `set_group_card` / `set_qq_profile` / `set_qq_avatar` / `set_group_notice` 等都登记在案，`qqControl: on` + 允许清单 + 危险闸三层过滤后才可能执行。**没有做自动同意好友申请的策略**：同意谁、拒绝谁是用户的事，先让探针盘点，再谈规则。

### 4. 探针先问「有什么」，再谈「用不用」

`scripts/qq-account-probe.ts`：只读，连 NapCat 跑一次，报告登录信息、好友数、群数、四个候选空间动作各自成不成、哪个能用，以及闸的演示（read 档下读放行、写拒绝）。报告只有动作名、条数、错误码，没有正文。

## 验证

- `account.test.ts` 9 项：默认关、只读档、未登记动作、允许清单、危险闸、一小时限流、审计不含正文、登记表合法性、盘点；
- `qzone-feed.test.ts` 4 项：三种数据形状、候选逐个试、全不通返回 undefined、摘要（只留文字 / 40 字 / 去重 / 条数）；
- `qzone-browse.test.ts` 4 项：开着读一页并进提示词、6 小时后不再提、试运行只写草稿、关着不读、睡着不读；
- 类型检查：`packages/bot`、`packages/koishi-plugin-qqbot` 都干净；`modules.test.ts` / `features.test.ts` 覆盖新文件和新开关。

## 没做 / 要注意

- **全都没在真 QQ 上试过**：空间动作名、好友申请字段、改头像要走的接口，都按 NapCat 源码和文档写，线上是否可用由 `qq-account-probe` 回答。
- **封号风险由用户承担**（用户 10-25 明说）。建议顺序：先只读盘点 → 再 `qzoneBrowse: dryRun` 看一周草稿 → 再 `on`；资料类单项开、看一天；社交和危险档最后，且每次一项。
- 允许清单是「写动作的对象」，不是「她能聊天的人」：她现在跟宝宝聊天不受这里影响。
- 审计里不写正文，但**对象（QQ 号 / 群号）和时间会留**；这是出事时唯一能回溯的东西。
