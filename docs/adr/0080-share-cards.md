# ADR 0080：他分享的链接、转发的聊天记录、发的文件，她看得懂

- 状态：**已实现，未上线**（分支 `claude/share-cards`；没有配置开关——只改他发来这几种消息时聊天记录里写成什么；上线要重启 Koishi，需要用户当次点头）
- 日期：2026-10-19
- 关联：[ADR 0052](0052-voice-and-images.md)（语音、图片怎么读）、[ADR 0051](0051-qq-faces.md)（小黄脸）、[ADR 0079](0079-poke.md)（同样是「以前她看不见」）
- 用户授权：2026-10-19 09:14「继续」——做和测；上线仍要用户在场点头。

## 背景

NapCat 把 B 站、小红书、网页、音乐、位置的分享当 `json` 段，合并转发当 `forward` 段，文件当 `file` 段。`segmentsToText` 只认文字、图、小黄脸、语音、视频，其余走 `default`：写成 `[json]`、`[forward]`，文件只写 `[文件]`。她收到的是一个看不懂的占位符。

真模型试过（`[json]`、`[forward]`、`[文件]` 各发一次，4 次）：对 `[json]` **装没看见**，接着问上一句（「问你呢，吃了没」「那就好，我还怕你又凑合一顿」）；对 `[forward]` 回「？」「这是啥，没看懂」；对 `[文件]` 回「发你的这都是啥啊」「说人话」。情侣之间发 B 站、小红书链接是很常见的事，这一下她就露馅了。

## 决策

1. **分享卡片**（`shares.ts` `shareText`）：解析 `data.data` 的 JSON，写成人看得懂的几个字：
   - 小程序（B 站等，`app` 含 `miniapp`）：`[分享：哔哩哔哩《原神枫丹新角色PV》]`——`detail_1.title` 是小程序名，`desc` 是内容标题；
   - 网页分享（`news`）：`[分享：小红书《标题》]`——`tag` 是站点名；
   - 音乐（`music`）：`[分享音乐：歌名 - 歌手]`；
   - 认不出结构：用卡片自带的通知栏那一行（`prompt`，例如 `[位置]学校那边大学西校区` → `[位置：学校那边大学西校区]`）；再不行 `[分享]`；坏 JSON 不抛。
   - **不放链接**：她点不开，也不该把网址写进聊天记录和长期记忆。标题去掉换行、方括号，超过 40 字截短。
2. **文件**：`[文件：创业基础小组作业.docx]`（有文件名就带）。
3. **合并转发**：`[转发的聊天记录]`。不取里面的内容（NapCat 的 `get_forward_msg` 可以取，但要多一次调用、里面可能是别人的聊天，先不做）。
4. 没有配置开关：这是纯输入侧的可读性修复，没有「关着」的理由；`[json]` 这种写法没有人需要。

## 验证

- 真模型（`sim/share-cards.json`，5 次，20 步）：
  - B 站分享：「枫丹这次的角色看着还挺好看的」「原神的？你玩的哪个角色」「枫丹又出新角色了？我都不玩这个，就知道你天天抽卡」——对标题有反应。
  - 小红书：「这个我可太需要了，看得我饿了」「收藏了，明天要不要去吃那家米线」。
  - 文件：「小组作业？你负责哪块」「创业基础？你自己的作业？」「发我干嘛」。
  - 转发：「这是啥，跟谁聊的」「转的啥，我这边没看到内容」——她看不到内容，这样问是对的。
  - 没有一次对分享装没看见。已知的小毛病：模型会顺着标题编一两个细节（「大学闺蜜带我去吃的那家米线好像就在里面」「我们组就我跟你啊」），和别的闲聊编细节一样，不是这一项带来的。
- 测试：`shares.test.ts` 5 项（小程序、网页、音乐、认不出结构、坏 JSON、换行方括号截短、文件名、与文字拼接）；bot 里和 `segmentsToText` 相关的 172 项（media、reply-timing、app、qq-faces、runtime、sim）全过；类型检查干净。

## 没做 / 要注意

- 没在真 QQ 上看过 NapCat 实际给的 JSON 长什么样——字段名是按我对 QQ 小程序、结构化消息的了解写的（`meta.detail_1`、`meta.news`、`meta.music`、`prompt`），认不出就退回 `prompt`，所以最坏是 `[分享：某某]`，不会比 `[json]` 差。上线后让他发一个 B 站链接、一个小红书链接，看日志里「收到」那一行的字数和她的反应。
- 合并转发内容、视频内容、位置的坐标都不读。她对视频仍是 `[视频]`。
- 红包、转账、群邀请等不是这三种段，仍按 `[类型名]` 写。

## 调整（2026-11-02，用户「检查类似的问题并修复」）

起因是 ADR 0081 那次线上人称错（引用没对上，她只看到「你这是说谁呢」）。同一类问题——**东西进她的提示词之前被丢掉、写错或认不出是谁说的**——又查出四处，都改了：

1. **合并转发**：原来只写「[转发的聊天记录]」（本 ADR 第 3 条当时说「先不做」）。现在 forward 段自己带 content 就用，只有 id 的问 NapCat（`get_forward_msg`）；写成「[转发的聊天记录（共 N 条，下面是前 8 条）：小王：……／他：……／你：……]」——**他写「他」、她写「你」、别人写昵称，不把别人的话写成他的**；每条 40 字、整段 360 字；取不到照旧只写「[转发的聊天记录]」。实时和补回两条路都做（`renderForward`、`app.ts` `fetchForwards`）。
   - 真模型（`sim/forward-{new,old}.json`，各 4 遍，他转发小王问「你女朋友是不是放你鸽子」、他否认、小王说她空间发了「又是一个人吃饭」，然后问「你看小王这人」）：新写法 4/4 认出是小王在八卦（「小王嘴真碎，还翻我空间？」「那条就是随口发的，昨天食堂一个人吃……」）；旧写法 4/4 看不到内容（「你发的记录我这儿就看见个标题，内容没过来」）。
   - 隐私：转发里是别人的话，会和他发来的截图一样进聊天记录和记忆；只放前 8 条、截短。
2. **认不出的消息段**：原来写英文类型名（「[dice]」「[rps]」「[mface]」「[location]」），现在写人话（「[掷骰子：5 点]」「[猜拳]」「[位置：……]」「[推荐了一个群]」……），真认不出的写「[一条特殊消息]」（`otherSegmentText`）。
3. **她发的语音**：`<<语音：…>>` 那一行从回复里摘掉后被 `historyText` 当内部标记剥掉，聊天记录里没有——他回「你刚那条语音……」她不知道自己说过什么；三分钟冷却跳过、没生成出来、发送失败时那句话直接丢。现在发出去记一行「[语音：…]」（带消息 id，他引用也对得上）；没发成语音就用文字发出去并记下。
4. **动电脑没干成时那句「这个没弄成，等下我再看。」**也记进聊天记录。

**没改、只记下的**：长期记忆里的事实是第三人称写的（「林梦瑶说……」「宝宝……」），可能让她用第三人称说自己；没有线上例子，截图那次已经由引用解释了，不盲改。私聊里的 @ 写成「@QQ号」，她认不出那是谁——私聊里几乎不用，做群聊时一起改。

测试：`context-segments.test.ts`（消息段人话、转发两种样子、别人的话不写成他的、取不到照旧；进应用：转发问 NapCat、语音发不了用文字发并记下）。
