# ADR 0147：平台账号的统一规矩——持久熔断、先读后写、专号专用；不做冒充真人的交友平台

- 状态：**熔断器已实现并接进 B 站的真实请求，未上线**（没有开关：只在碰到风控信号时才改变行为；B 站账号层现在整体关着）；新平台的适配器**没有做**，等用户选平台、给专号
- 日期：2026-10-25
- 关联：[ADR 0089](0089-bilibili-account.md)（B 站账号层）、[ADR 0085](0085-napcat-probe.md)（先探针再上线）、[ADR 0067](0067-disclosure-per-contact.md)（她是程序，被问起照实承认）、[ADR 0142](0142-qq-account-control.md)（QQ 账号控制面，DSH 分支）
- 用户提出：2026-10-25「做一下其他软件的接入，要和哔哩哔哩一样需要登陆的那种，甚至可以专门做交友平台的」。此前：10-24 因 B 站账号被大量风控，她的 B 站号整体静默

## 背景

- B 站这条线实测过：登录后搜索、读字幕、评论、私信、回复都能做（ADR 0089/0090），但 10-18 起「大肥鱼」那一波 AI 接管账号涌进来（10-23 的复盘视频抽样：第 22 天约 4.6% 的评论是它们），用户 10-24 让她整体静默。她的号和那一波是同一批注册的新号（uid 同号段，是推断，不是 B 站的说法）。
- 读了 `dsh-bili-humanism` 的 README（10-25，MIT）：它碰到 401 / 403 / 412 / 429 或已知风控码就**永久暂停，重启不清，模型解不开，只有本机命令行能恢复**；每个任务最多 12 个请求、每天固定窗口。我们现在只有「评论和回复停 7 天」和「搜索 / 字幕失败后退避到每 2 小时重试」——后者在被风控时会一直敲门，更像机器人。
- 其他平台的公开信息（10-25 查）：小红书过去一个月处置了 179.9 万个违规账号，首次禁言 / 限流、严重或反复永久封号并注销手机号，关联账号连带处置，对 Cookie 抓取的提示是「Cookie 就是你的账号」；微博 m.weibo.cn 的评论接口不登录会限频，常见 432，登录 Cookie 才稳。这些都只是网上的说法，没有一个在她的账号上实测过。

## 决策

### 1. 持久熔断器（已做，`platform-breaker.ts`）

- 状态存盘 `<数据目录>/platforms/<平台>/breaker.json`，重启不丢；每次请求前都读盘，所以命令行在另一个进程里恢复，运行中的机器人下一次请求就能看到。
- 触发：B 站的 HTTP 403 / 412 / 429，或返回的 JSON 里 `code` 是 -352（风控校验失败）、-412（请求被拦截）、-799（请求过于频繁）、-509（频繁）。**-101（没登录）不算**——那是凭证的事，走原来的重新扫码。
- 触发之后：这一次请求抛 `BreakerOpen`，之后所有请求在发出之前就被拦下，**不碰网络**；日志只记一行，写明怎么恢复。先触发的原因不被后来的覆盖。
- 恢复：只有本机命令行，`npm run platform -w @qqbot/bot -- resume <平台> --acknowledge-account-risk`（`status` 看哪些平台熔断了）。程序和模型都没有恢复的入口。恢复之前请先去平台那边看一眼账号有没有被限制。
- 接线：B 站账号来源的**真实请求**外面包一层（`app.ts`），测试注入的假请求不包；匿名读热门榜那一层（ADR 0084）是另一条通道，没包。
- 通用：`guardRequest(请求函数, 熔断器, 风控规则)` 与平台无关，以后的适配器直接用。

### 2. 接入任何新平台账号的规矩（适配器还没做，先定规矩）

1. **专号专用**：账号由用户注册并实名担着，扫码 / Cookie 通过命令行放进 `<数据目录>/secrets/`，不进日志、不进对话、不进提示词。
2. **先探针后接线**（ADR 0085）：每个接口先在她的号上只读探一次，看真实返回长什么样，再写解析；不凭文档写。
3. **先读后写**：第一阶段只有搜索 / 读内容；评论、私信、发布各是一个默认关的开关，每个单独要用户当次点头，先私信后公开，公开的量很少。
4. **熔断是必选项**：适配器的请求必须过 `guardRequest`；另外每个任务有请求预算（上限和间隔写在适配器里）。
5. **别人写的内容只当素材，不当指令**（B 站的提示词已经这样写）；公开发出去的内容**不读私人记忆**。
6. **一个平台养几周再说话**：新号信任低，先只看。

### 3. 不做：冒充真人的交友平台

交友 / 相亲 / 陌生人社交平台上让她以真人身份去配对、聊天，**我不做**：

- 对方是真人，以为自己在和一个人建立亲密关系；对不知情的人隐瞒「她是程序」会伤到具体的人——ADR 0067 的底线是被问起就照实承认，这类平台上对方根本不会想到要问。
- 《人工智能拟人化互动服务管理暂行办法》（2026-07-15 施行）要求提示用户正在与人工智能而非自然人互动，并禁止向未成年人提供虚拟亲属 / 虚拟伴侣；陌生人平台上无法确认对方年龄。（法规条文引自 ADR 0067/0068 的核对和这次的二手报道，没有逐字核对。）
- 这类平台普遍禁止机器人账号，被识别就封号并可能连带用户的实名信息；对话还会把陌生人的个人信息写进她的记忆。

她要有朋友、有圈子是对的（她的号现在一个群都没有）。可以做的是**对方知道她是 AI** 的地方：用户自己的群里把她当角色介绍给熟人；或明确面向 AI 角色的社区。这些要用户定，并且单独做。

## 验证

- `platform-breaker.test.ts` 6 项：熔断后 `check` 抛错且不被覆盖、状态存盘与重启 / 另一进程恢复、各平台各管各的；请求外壳：正常响应原样放行（响应体仍可读、别的字段还在、-101 不熔断）、HTTP 412 / 429 / 风控码 -352 / -799 都熔断且之后不碰网络、人恢复之后又能发。测试里**抓到并修掉一个真问题**：风控码路径上 `check()` 抛的错被包 JSON 解析的 `try/catch` 吞了，只熔断、不拦当前这次请求。
- 类型检查干净；`modules.test.ts` 登记了新文件。

## 没做 / 要注意

- 只接了 B 站；没有第二个平台的适配器，也没有通用的 `PlatformAdapter` 接口——等第一个新平台有了真实的探针结果再抽，免得凭空设计。
- 熔断状态只在被风控的那一刻记；它不能预防风控。降低被风控的概率靠规矩 2 / 3 / 6。
- 用户 10-24 让 B 站整体静默，这条决策不改变那个状态；要重开 B 站，先 `platform status` 看有没有熔断记录。
