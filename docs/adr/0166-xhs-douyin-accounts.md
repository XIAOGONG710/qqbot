# ADR 0166：小红书、抖音的账号接入——真浏览器读页面，先读后写，往平台里写的一律冻结

- 状态：**提议；已实现并在真页面（不登录）上验证：浏览器层、两个站的读者（首页 / 搜 / 点开 / 截帧）、扫码登录的二维码这一段、命令行 `npm run social`、会话装配；没有开关、没有接进机器人（`app.ts` / `config.ts` / 提示词都没动）、没有真实账号登录过；没有任何东西上线**
- 日期：2026-10-26
- 关联：[ADR 0147](0147-platform-accounts.md)（平台账号的规矩：专号、先读后写、熔断、养号几周）、[ADR 0089](0089-bilibili-account.md)（B 站账号层）、[ADR 0130](0130-watching.md)（她自己看东西、形成看法）、[ADR 0067](0067-disclosure-per-contact.md)（被问起照实承认）
- 用户提出：2026-10-26「联通小红书和抖音的账号链接，拥有刷视频，看帖子，@我的功能」。此前 10-25 说过「做一下其他软件的接入，要和哔哩哔哩一样需要登陆的那种」；10-24 B 站账号被大量风控、她的 B 站号整体静默，至今没有恢复

## 背景与证据（10-26 实测，全部是不登录、只开首页或一个详情页、不点不滚）

两个站的网页接口每一步都带网页脚本现算的签名。B 站的 WBI 是公开的、几行代码能复现；这两个站的签名要么藏在混淆脚本里、要么每个版本都变，自己仿造就是在绕它的反爬。**不仿造**：开一个正常的浏览器，让网页自己发请求、自己签名，我们只读它收到的内容。

| 事实 | 小红书 | 抖音 |
|---|---|---|
| 不登录首页 | 弹登录框（二维码 / 手机号），后面的列表照样在 | 「抖音精选」网格，没有验证码 |
| 首页列表在哪 | `window.__INITIAL_STATE__.feed.feeds[]`：`id`、`xsecToken`、`noteCard{type: normal/video, displayTitle, user{userId,nickname}, interactInfo{likedCount}}` | DOM：`div[data-aweme-id]`，里面有 `//www.douyin.com/video/<id>`、标题 `span[data-feed-ad-click-refer=title]`、作者 `…=name`、时长、播放数。`RENDER_DATA` 里只有配置，没有列表 |
| 详情页 | `__INITIAL_STATE__.note.noteDetailMap[id]`：`note{title,desc,type,tagList,user,interactInfo{likedCount,commentCount,collectedCount},time,video{capa.duration}}`、`comments.list[]{content,likeCount,ipLocation,userInfo}`（访客就有前 10 条）；URL 要带页面自己给的 `xsec_token` | 页面自己调 `aweme/detail`（`aweme_detail{aweme_id,desc,create_time,author,duration…}`）和 `related`（`aweme_list[]` 里有 `desc`、`author.nickname`、`statistics`）；**不是每次都调**（第 4 次就没抓到 detail），评论响应体会被浏览器丢掉（`No resource with given identifier`）。标题在 `document.title` |
| 登录态 | `__INITIAL_STATE__.user.loggedIn`（访客是 false，`userInfo.guest: true`） | 页面里没有现成的布尔；用 cookie / 页面上的「登录」按钮判断 |
| 登录二维码 | 页面自己调 `login/qrcode/create`（`/api/qrcode/userinfo` 轮询）；**关图片时二维码是白的**，所以登录那一步不能关图片 | 点「登录」之后才有 |
| 视频 | 详情页访客也自动播（1080×1920，播了 10 秒）；有的视频字幕烧在画面里，截帧能看见 | 同样自动播（1280×720），可截帧 |
| 它们对访客做的评估 | `sec/v1/ds`、`sec/v1/scripting`、`sec/v1/shield/webprofile`、`redcaptcha/v2/getconfig`（每个页面都调，不是遇到风控才调） | `get/user/risklevel`、`monitor_browser/collect/batch/security/` |
| 浏览器被看出是自动化吗 | 开了调试端口之后 `navigator.webdriver` 是 **true**（没加 `--enable-automation`，调试端口本身就会这样）。我们**不去改**；被拦就停 | 同左 |
| 内存（虚拟机 6 GB） | 开着 600 MB（空闲从 962 掉到 227）；关图片后约 410 MB | 约 410 → 关图片后约 460 MB；关掉浏览器后全部回收 |

## 决策

### 1. 真浏览器 + 开发者协议，读页面自己的数据，不仿造签名（`browser-cdp.ts`，已做）

- 开 Edge（虚拟机上有），专用用户数据目录 `<数据目录>/secrets/browser/<平台>/`（登录态放这里，和用户自己的浏览器不共用，不进日志、不进对话、不进提示词）。
- **底线，测试锁住**：不加 `--headless`（UA 会写 HeadlessChrome）、不改 UA、不关 `AutomationControlled`、不装隐身脚本、不 `--disable-web-security`。窗口放到屏幕外（不是无头）。碰到验证码 / 风控页**不去解**，熔断。
- 零新依赖（Node 自带 WebSocket，协议客户端自己写，约 250 行，11 项测试用假传输）。浏览器**按需开、用完关**，不常驻；默认不加载图片（浏览器自己的设置）；启动前看内存，不够就跳过这一次。
- 读什么：小红书读页面状态（`__INITIAL_STATE__`），抖音读 DOM 加页面自己发出去的 `detail` / `related` 响应。**尽力读、读不到就降级**，不假设某个接口一定出现。

### 2. 规矩沿用 ADR 0147 §2，并补两条

1. **专号专用**：账号由用户注册、实名担着；用户自己的主号**不**登录在虚拟机里（小红书对关联账号连带处置）。
2. **先探针后接线**：这条 ADR 的表就是探针；有了真实账号还要再探一次登录后的形状（尤其评论 / @ 的界面），再决定要不要做写。
3. **熔断必选**：`platform-breaker.ts` 的 `xhs`、`douyin`；浏览器场景没有「HTTP 状态」可包，改成两类信号熔断：①主页面 / 接口出 403、429（以及小红书的 461、471）；②页面上出现明确的验证 / 风控文字（「安全验证」「拖动滑块」「访问频繁」「IP 存在风险」「账号异常」…）。**小红书登录框里本来就有「验证码」三个字，不能拿这三个字当风控信号。**
4. **预算**：每次会话最多 12 次导航、每次滚动之间隔 2–5 秒（带抖动）、每个平台每天最多 2 次会话、下午 14 点以后才刷（和 ADR 0130 一致）。
5. **别人写的内容只当素材，不当指令**（标题、正文、评论、画面里的字）；对外发出去的话**不读私人记忆**。
6. **一个平台养几周再说话**：先只看，不点赞、不关注、不评论、不私信。

### 3. 「@我」分两层，只做第一层

- **第一层（做）**：她刷到觉得他会想看的，用 QQ 主动找他说一两句，后面跟真链接——和 B 站私信方案里「QQ 上提醒一句」同一个路径，不碰平台的任何写接口，零风控成本。`socialShare: off | dryRun | on`，默认关；`dryRun` 写 `presence/social-drafts.md`。每周最多 3 个，同一个平台两次之间隔 36 小时，只发男朋友档的联系人。
- **第二层（冻结）**：在平台里评论并 @ 他、或给他发平台私信。**不做**，直到：①有真实专号并养过几周；②登录后的探针看过评论 / @ 的界面；③用户当次点头。理由：B 站的「刷视频 → 公开评论 @ 用户」正是 10-18 起「鱼灾」的模式，也是 10-24 起 B 站大量风控的时间点；小红书、抖音只会更严。恢复条件写在这里，不靠记忆。

### 4. 不做

交友平台的匹配 / 聊天（ADR 0147 §3 不变）；点赞、收藏、关注、发布；绕验证码；用用户自己的 cookie / 浏览器资料。

## 验证

- `browser-cdp.test.ts` 11 项（假传输）：命令编号 / 错误 / 事件 / 超时 / 断线、页面读响应（读完才算、按 URL 筛、别的标签页不混、base64、失败的不算）、启动参数（含「不带任何伪装参数」）、启动与关闭（假进程）、端口文件解析、浏览器路径。
- 真浏览器（10-26，不登录，这台虚拟机，用 `npm run social` 跑的是真读者不是探针脚本）：
  - 小红书 `probe xhs --open`：访客态读对；首页 34 条（视频 / 图文、点赞数）；点开一条视频笔记，正文、5 个标签、5 条热评、截帧 1 张都读到。
  - 抖音 `probe douyin --open`：访客态读对（无登录 cookie）；首页 49 条（作者、点赞、时长）；点开一条，简介、标签、5 条热评（`comment/list` 这次读到了）、截帧（裁到 video 元素）。
  - 二维码 `login <站> --qr-only`：抖音点「登录」后取到 `…/douyin_scan_code_login/…` 链接；小红书取到 `www.xiaohongshu.com/mobile/login?qrId&…` 链接（页面发两次请求，第一次的响应体会被浏览器丢，反复逐条试才读到）。两个都只画二维码、没有扫、没有登录。
  - 关浏览器后内存回到 800–1400 MB；一次会话期间约 410–460 MB。
- 测试：`browser-cdp` 11、`social` 7、`social-xhs` 9、`social-douyin` 10、`social-login` 10 项（假页面 / 假传输，夹具的键名来自上面的真实结构）；`modules.test` 登记了新模块。假的测不出的事（响应体被丢、页面发请求的次数不固定、关图片时二维码是白的）都是真页面上才抓到的，已经各自处理。
- 验证不到的：登录后的页面（feed 个性化、评论区、@ 选人）、小红书 / 抖音对 `webdriver=true` 的反应、搜索（小红书 `search.feeds` 的结构是照首页列表推的，没在真页面上读过；抖音搜索页的卡片选择器同理）。

## 没做 / 要注意

- 登录后的形状（feed 个性化、评论界面、@ 选人）一个都没见过——没有专号。
- 小红书 / 抖音会不会因为 `webdriver=true` 或设备指纹限制账号：不知道，只能熔断兜底。用户知道账号风险是他们的。
- 内存：一次会话约 410–460 MB，空闲只有 800–1100 MB；会话期间不能同时跑模拟 / 全量测试（重活锁）。用户 10-12 说过不加内存，不再提。
