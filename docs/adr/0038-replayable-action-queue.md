# ADR 0038：行动先排队，结束后才成为事实

- 状态：模拟器增量已实现、已验证（2026-10-08）
- 关联：[ADR 0029](0029-life-event-ledger.md)、[ADR 0037](0037-typed-life-actions.md)、[长期执行计划](../plans/2026-10-08-long-term-execution.md)

## 问题

类型化行动裁判能判断一个动作是否合法，但动作通常有持续时间。若计划一开始就写进 `events.json`，未来的结束时刻会被当成已经发生的事实；若只存在内存里，Koishi 重启后行动会消失或重复结算。

## 决策

新增原子文件 `action-queue.json`，保存已经由世界裁判确定、但尚未结束的行动。队列里的 `event.at` 是预计结束时刻；只有虚拟时间到达该时刻以后，事件才交给统一事件账。

结算严格按以下顺序：

1. 将同一个稳定 ID 的事件提交给 `WorldState.recordEvents()`；
2. 重新读取事件账，确认该 ID 已经存在；
3. 再从行动队列移除并原子写盘。

若进程在第一步后、第三步前退出，重启后仍会再次提交同一个 ID；事件账幂等去重，然后队列安全清除。写事件失败或事件没有真的进入账本时，队列保持不动。

模拟器新增 `action` 步骤。场景只提交动作意图、目标和期望时长，不能直接声称 `succeeded`；裁判失败会立刻留下失败事件，成功或中断则排队，时间推进到结束以后才入账。旧的 `life` 步骤继续兼容。

## 验证

- 行动裁判、队列与模拟器定向测试 24 / 24；
- 覆盖：排队落盘、结束前无事实、结束点结算、重启恢复、同 ID 幂等、写账失败保留、写账静默失败保留、损坏项目过滤、模拟场景重放；
- 全仓测试 525 / 525（bot 465、character-tools 37、Koishi 插件 23），三套 TypeScript 类型检查通过；
- 本增量只接模拟器，不启动线上自主行动，不改变当前聊天和作息行为。

## DSH 复核之后的调整（2026-10-08 晚，Claude）

DSH 侧静态复核了 `d03b057`、`b5f2a6f`（`exchange/reviews/2026-10-08-action-engine-review.md`），结论是「裁判干净，队列还不够接执行器」。逐条核实后改：

1. **队列里还没结算的计划也算占用**（复核 1.1，核实成立：`schedule` 只看事件账）：排队时把队列里别的计划当成事件账里的事交给裁判。
   撞在计划中间的 `conflict`；灵活的行动撞到后面的计划时提前停（`interrupted`，和撞到课一样）；同一顿饭排两次第二次 `already_done`。
2. **账本不收的挪到死信区，写账抛错不往外抛**（复核 1.2；2.1 核实成立：`world.ts` 的 `append` 遇到格式不对、结束时刻在账本时钟之后、日子在开学前的草稿是静默 `continue`）。
   原来这两种都让 `settleDue` 每次抛同一个错、卡在这一条，测试还把这个当成了对的。现在：
   - `recordEvents` 抛错（写盘失败这类一会儿就好的）：记日志，这条和后面的留着（按结束时间的顺序），下次再试；
   - 写了但账本里没有这一条：挪进 `action-queue.json` 的 `dead`（带 `deadAt`、`why`），记日志「事件账没收，挪到死信区」，不再重试，后面的照常结算。
3. **取消、改时间**（复核 1.3）：`cancel(id, at, reason)`——at 时还没开始的记成 `failed`、原因「取消：下雨了」，开始了的在 at 这一刻打断成 `interrupted`「打断：肚子疼」；
   都留在队列里等结算落账（她记得「本来要去图书馆，下雨没去」），那段时间空出来能排别的；做完了的取消不了。
   `reschedule(id, at, { startedAt, durationMinutes })`——还没开始的按新时间重新裁判、同一个 id，新时间不行就照原计划；开始了的只能 `cancel`。
4. **结算挂在读世界之前，和世界用同一个时钟**（复核 3·4、2.2）：`settlingWorld(world, queue, nowFn)` 包一层，`at`、`note`、`events`、`actions` 之前先 `settleDue`。
   模拟器里只有 `wait`、只有聊天的场景也会结算（原来只有 `advance` 步骤之后才结算）；以后线上装配也走这一层，不另起定时器、不会有两个时钟。
5. **裁判**（ADR 0037）：`alreadyDid` 按她的一天算（和事件账的 `day` 一致，复核 2.3）；**睡觉可以在入睡时刻前三个半钟头内任何时候开始**（她 02:00 睡：22:30 早点睡、熬到一两点都行，过了 02:00 还没睡也行），
   都睡到那一晚该起的时候；原来只能正好 02:00 睡（复核 1.5）。白天的「睡」是 `rest`。

复核 2.4（`typedOccupation` 没有生产调用方、状态行还没接行动结果）属实，是下一增量（执行器、线上装配）要做的，不在这次。

2026-10-08 23:55 上线（用户选「现在上线」，`main` 快进到 `9a2bf9e`，重启 Koishi，启动日志无错误），线上还没有装配点，行为不变。

验证：`action-queue.test.ts` 8 项（重叠、取消、改时间、死信、读世界前结算），`actions.test.ts` 7 项（早睡 / 熬夜、她的一天）。
