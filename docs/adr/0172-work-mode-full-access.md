# ADR 0172：工作模式给整机权限——用户已授权；本地接口加守卫

- 状态：**已实现，随 `dsh/qq-control` 提供；本机的常驻进程和 Koishi 要重启才生效**
- 日期：2026-10-29
- 关联：[ADR 0148](0148-device-control.md)（设备控制：分档 + 批准）、[ADR 0171](0171-self-directed-memory.md)、`docs/plans/2026-10-27-soul-plan.md`、`exchange/reviews/2026-10-29-claude-review-dsh-10-27-to-29.md`（P0-1）
- **用户决定（2026-10-29，当前会话）**：「工作模式给予整机权限」。这是对审查 P0-1 的回答：用户知道工作桥用 `DSH_PERMISSION_MODE: 'danger-full-access'` 起智能体、工作目录是桌面，并明确要这个权限。

## 背景

`work-bridge.ts` / `scripts/her-resident.mjs` 把 QQ 工作模式下男朋友档那位发的每一条非斜杠消息交给 headless 的她，权限是整机权限（`danger-full-access`）。10-29 审查时发现两件事：

1. 权限比用户 10-25 选的 ADR 0148（分档 + 批准）大得多，当时不确定用户是不是明确要了——**现在确认了：要**。
2. 常驻进程的本地接口（`127.0.0.1:7777`，`POST /task` 等）**没有任何认证，也不看 Origin / Host / Content-Type**：本机任何进程、用户浏览器里的任何网页（`Content-Type: text/plain` 的「简单 POST」不触发预检）都能排一个任务给整机权限的智能体。

## 决策

### 1. 整机权限保留，给「他从 QQ 发来的任务」

默认 `danger-full-access` 不变（用户授权）。两处写死的字符串收成一个设置：环境变量 `HER_PERMISSION_MODE`（空 = 整机权限）。以后用户想降档，只改这一个环境变量并重启常驻进程 / Koishi，不用改代码。

**授权范围**：QQ 工作模式（`/dsh` → 她答应 → `work`）下他发的任务。**不包括**常驻进程无人值守的「睡眠整合」「随机醒来」两类自主运行（它们用同一个常量，所以现在也是整机权限）——用户的话只提了工作模式，这两类**没有被明确授权**，保持原状但在这里记一笔：醒来提示词会让她按自己的兴趣清单（她自己能改）上网查资料，网页内容是注入面，而 `soul_update` 能把内容写成每轮注入的系统提示词。这一项等用户另行决定。

### 2. 本地接口守卫（`platform/resident-guard.ts`，纯函数 + 令牌文件）

整机权限是给用户的任务，不是给本机别的进程和浏览器里的网页，所以：

1. `Host` 必须是 `127.0.0.1:<端口>` 或 `localhost:<端口>`（挡 DNS 重绑定），否则 400；
2. 带 `Origin` 头的一律 403——浏览器的跨站请求都会带；
3. 除 `GET /health`（探活）外都要共享令牌 `X-Her-Token`（定长比较），否则 401；令牌是常驻进程第一次启动时随机生成的 64 位十六进制，存在常驻进程自己的目录（`HER_DIR`，默认 `C:/Users/22601/.dsh/her`）下的 `RESIDENT_TOKEN`，只在用户目录里；
4. `POST` 必须是 `application/json`，否则 415。

工作桥读同一个令牌文件、请求时带上。**常驻明确回 401 / 403 时，工作桥抛错，不再悄悄改走临时 headless**——那样会绕过常驻的任务队列和「她离开电脑」（`go_offline`）。只有「连不上常驻」才走临时 headless，和以前一致。

### 3. 不做

- 不削减能力：任务做什么、用什么权限，仍由用户授权的整机权限决定；
- 不加「批准」环节（ADR 0148 的做法）：用户选了整机权限。想要就把 `HER_PERMISSION_MODE` 降档；
- 不动自主运行（见 1），不动 `soul_update`、`outbox`、`recallWork` 等审查里的其他发现——各自单独处理。

## 验证

- `resident-guard.test.ts` 11 项：守卫的每条规则（含「令牌对但带 Origin 也拒」「没有 Host 也拒」「长度不同的令牌」）、令牌生成 / 复用 / 坏文件重生成、权限模式默认与降档、工作桥带令牌并拿到回复、401 / 403 不改走临时 headless，以及**把真的 `scripts/her-resident.mjs` 起成子进程**：无令牌 401、错令牌 401、带 Origin 403、`text/plain` 415、伪造 Host 400、带令牌的 `GET /life` 200、`GET /health` 不要令牌，日志里有 `rejected` 记录。接线测试**不发任何合法的 `/task`**（在装了 DSH 的机器上那会跑起真的智能体）。
- 变异检验：把常驻脚本里的守卫调用关掉，接线测试变红；恢复后 11/11。

## 要注意

- **要两边都重启才完全生效**：常驻进程（生成令牌、开始检查）和 Koishi（工作桥开始带令牌）。顺序无所谓：新常驻 + 旧桥 → 旧桥收到 401 → 旧桥会改走临时 headless（能用但绕过队列）；旧常驻 + 新桥 → 令牌头被忽略（照常工作，但还没有保护）。两边都新才是目标状态。
- 令牌文件靠用户目录的权限保护；同一 Windows 用户下的任何进程都读得到它——这挡的是**网页和别的用户**，不是同一用户下的恶意进程（那已经是整机权限能干的事）。
- `GET /life` 现在也要令牌（里面有她最近的事件，含他说过的话的前 40 个字）。
