- 状态：**已实现，未上线**（2026-10-22；配置 `lagTail`；默认关）。上线 = `koishi.yml` 里加 `lagTail: true` + 重启；回滚 = 改回 false + 重启（不存任何状态）
- 日期：2026-10-22
- 关联：[ADR 0007](0007-schedule-and-reply-timing.md)（什么时候看到）、[ADR 0075](0075-reply-rhythm.md)（打字按字数 + 看想）、[ADR 0013](0013-old-project-advice.md)（冷场延迟、看心情不回）
- 用户提出：2026-10-22「把你提出的这些差距都进行补平，真人怎么样就让她怎么样」（差距之一：回复延迟没有长尾）

## 差距（有数据）

- 线上（10-22 00:36 以后，53 轮）：她第一条的延迟中位 8.3 秒，中间一半在 7.2–9.6 秒，**没有一次超过 1 分钟**；10-05 到 10-22 全部 438 轮里 ≥ 60 秒的只有 2%，≥ 10 分钟 0%。
- 真人：公开数据里 WhatsApp 111 人的回复只有 **57.8% 在 1 分钟内**（arXiv 1802.03393）；IM 回复时间取决于对方在不在手机上、手上有没有别的事（Avrahami & Hudson 的模型预测 30 秒 / 1 / 2 / 5 / 10 分钟内会不会回）。情侣聊得热的时候 1 分钟内的占比比平均高，但一定有一条尾巴：做别的、手机在别处、洗澡、走路。
- 原因：`whenSeen` 里“正聊着”是**马上看到**，“冷场”是 15–60 秒，之后“看 + 想”（ADR 0075）最多 28 秒。这些加起来是一个窄分布，没有长尾。

## 做了什么

1. **分心的延迟**（`reply-timing.ts` 的 `distractionMs`，开 `lagTail`）：醒着、空着时（睡着、上课、洗澡、危机各有各的规则，不动），按第一条没回的消息 id 定下来（同一串重算多少次一样）：
   - 是否分心：一来一回很快（她上一次回复离这一串不到 90 秒）10%，正聊着（10 分钟内）30%，冷场 45%；23 点到 2 点手在手机上，×0.8；他在难受 / 不舒服 / 问她在不在（`难过|难受|不舒服|烦死|累死|哭|崩溃|生病|发烧|疼|在吗|在不在|人呢`），×0.4 且最多 1 分钟。
   - 分心多久：55% 20–75 秒、28% 1.5–5 分钟、13% 5–20 分钟、4% 20–60 分钟。
   - 日志里“正聊着；在做别的，3 分钟后才看到”。
2. **断网很久才回**（`responder.ts` 的 `failingSince` + `time-context.ts`）：回复一直失败（连不上模型 / 网断了）十分钟以上才终于发出去时，时间块里多一句：你这边有一阵子（约 N）一直连不上网，他的消息刚才才收到；他问起或你顺口想解释，说一句“刚才网断了 / 没信号”就行，别编别的原因，也别道歉过头。发出去之后清掉。（10-14 到 10-21 她有 86 小时左右回不了话，原来补回时只有“到现在过了 N 小时”，没有原因。）

## 没做 / 要注意

- 只改“什么时候看到”，不改打字时间；已读（`readReceipts`）在“看到”那一刻才发，所以对方这几十秒到几分钟看到的是“未读”，和真人一样。
- 一小时的上限；超过一小时没回要么是睡着 / 上课（原规则），要么是掉线。
- 他连着发几条时，延迟按第一条算，期间来新消息会重算（原来的机制）。
- 她主动说“才看到”这种话由模型自己决定；`lagTail` 不给台词。

## 验证

- `reply-timing.test.ts`「回复延迟的长尾」：没开原样、开了的分布、他难受时更快且 ≤ 1 分钟、同一串每次一样、睡着 / 危机不受影响、理由写明；`time.test.ts`「断网很久才回」；`runtime.test.ts`（失败之后才发出去，生成时知道从哪一刻起；发出去之后清掉）。
- 回滚：`lagTail: false` + 重启。
