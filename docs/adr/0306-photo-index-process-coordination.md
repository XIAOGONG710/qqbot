# ADR0306：照片索引跨进程协调，JSON 保持唯一事实源

日期：2026-11-05

## 证据与决定

ADR0232 的顺序版本检查不能覆盖同时读改写：两个真实独立进程都通过检查、停在 rename 前再释放，两次 add 成功但 JSON 只有一条。活 bot 与 photo-cli 必须共同参与同一协议，不能靠写前再比较一次或读 PID 后删除锁。

使用 Node 24 内置 `node:sqlite` 的 `DatabaseSync`，在货架目录的 `index.coordination.sqlite` 上 `BEGIN IMMEDIATE` 获取操作系统维护的写锁。SQLite 仅作协调器，不存照片元数据。每次短同步变更持锁后重新读取并验证 JSON，再按当前操作增量计算、原子发布 JSON，最后 ROLLBACK/close 释放锁。JSON rename 是唯一数据提交点；不迁移 v1 索引、不覆盖未知兼容字段、不依赖 SQL 表的内容。

搜索、下载、模型判断全部在锁外；其后提交重新检查 seen、容量、菜名与猫的系列身份，迟到结果不能复活已删除条目。add/remove/used/seen 使用相同协议，陈旧实例不能把旧快照重新写回。公开读取刷新原子 JSON 快照；无照片引用的普通文字，以及明确禁用照片的清理不读索引。真实照片引用仍在坏索引时失败关闭。

app 停止时取消货架发现生命周期，每个异步阶段结束后检查停止信号，晚返回/拒绝不再开始下一阶段或写 seen/索引。沿用兼容的来源接口，不声称能硬停自定义不合作来源；停止信号保证晚结果不再改变货架，不等待这些不合作承诺才关闭 app。

SQLite busy 等待预算为 50ms；这是获取锁的等待预算，不是同步文件 IO 的整体截止。只将 SQLite BUSY/LOCKED（含扩展码）视为可重试，发现任务返回既有 retry，CLI 明确提示稍后重试。损坏、IO、目录障碍失败关闭，不能降级为无锁写，也不自动删除/隔离协调文件。进程退出由 OS 释放锁，不使用 PID、生存时间或自行删除“陈旧锁”的竞争协议。

JSON 写入若实际 rename 后抛错，在同一锁内读回确认结果；完全相同才认定本次已应用，不重放 used 增量。释放锁或日志回调异常不能把已发布成功变成可重试失败，也不能覆盖原始业务异常。每次操作关闭 SQLite 连接，避免 Windows 文件句柄跨生命周期滞留。

照片 resolve 保存有界说明快照供已发送历史使用，缓存失效或索引后来损坏不能抹掉已发送事实；真实发送链须绑定本次解析得到的说明，不能让同 ID 的另一在途发送覆盖该事实。快照不参与可发送性或权限判断。

## 验证与兼容边界

独立进程覆盖同时 add/used、remove 防复活、活实例读刷新、rename 前后强杀、锁竞争、坏库、目录障碍、发布前 IO 失败、发布后异常与再次恢复。真实 photo-cli 与假 bot 的集成测试确认 bot 无需重启即可发现新增图；测试只使用合成图片和假传输。故障注入检查原 JSON、未知字段、增量次数与后续可重新获取锁，不以诊断脚本退出成功代替正确性断言。诊断脚本现在断言两次成功、两条持久记录且不同时进入发布区。

部署须停止旧写入进程，再统一使用新协议；旧版本、外部直接编辑 JSON、替换/删除协调文件不在协调保障内。协调文件不可在写入进程运行时删除或重建；损坏时停止全部写者，人工检查恢复，不能把损坏当作自动重置依据。只承诺正常本地文件系统的互斥，不宣称网络文件系统或恶意文件替换安全。

进程在 JSON 发布前退出保留旧数据，发布后退出保留新数据；没有第二个 SQL 数据提交点。图片和索引仍不是跨文件事务，失败可能留下不可发送的孤儿图。不新增断电 fsync 保证，也不声称对调用方丢失成功回复后的任意增量重试实现 exactly-once；后者需要操作身份协议。
