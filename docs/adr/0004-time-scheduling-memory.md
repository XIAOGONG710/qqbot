# ADR 0004：按调研方案在运行时实现时间感、消息调度与长期记忆

- 状态：已采纳（2026-10-04 与用户确认，见文末「确认记录」）
- 日期：2026-10-04
- 依据：[SillyTavern × QQ 虚拟伴侣：事实核对、角色表达与记忆调试方案](../research/2026-10-03-companion-research-and-debug-plan.md)（下称「方案」）
- 关联：[ADR 0002](0002-standalone-runtime.md)（运行时独立于 SillyTavern）、[ADR 0003](0003-contact-tiers.md)（分档）

## 背景

方案按「SillyTavern + QQ 桥接器 + 记忆插件」来写。本项目按 ADR 0002 不在 SillyTavern 里运行，
方案里的记忆路线、Summarize、Regex 等要先对应到运行时，才能决定做什么、按什么顺序做。

### 取证

**运行时（main `8300e73`）已经覆盖方案 2.1 处理顺序里的这些环节：**

- 身份与会话：白名单按 QQ 号，聊天记录按联系人分文件（`runtime/bot/chats/<QQ>.jsonl`），每条带时间、角色、QQ 消息 id。
- 去重：补回漏掉的消息时按 QQ 消息 id 去重。
- 生成中来新消息：丢掉草稿，带上新消息重新生成（最多 2 次）。
- 只有发出去的消息进聊天记录，发送失败的不记。方案 5.4 说的「只有已发送消息进入共同经历」在运行时天然成立。
- 清理与拆条：去掉名字前缀，按行拆成多条，间隔 1 秒。

**还没有的：**

- 时间：提示词里没有任何时间信息。实测她把周日说成周四（roadmap M3）。
- 连发合并：没有静默窗口，第一条一到就开始生成，后面几条靠「丢掉重来」补上。
- 过时气泡：拆成几条发送时，中途来了新消息，剩下的仍会发完。
- 长期记忆：只有聊天记录本身。

**上下文能装多少原文**：用林梦瑶的卡和世界书、`maxContext` 8192、`maxTokens` 300，拿一位联系人 133 条真实记录实测：
固定部分约 2,230 token（ST 兜底估算），每条消息平均约 11 token，133 条全部放得下，剩余预算约 5,600 token，约合 500 条。
这 133 条是 54 分钟里聊的，照这个密度，几个小时之后最早的原文就会被截掉，之后靠什么承接是记忆要解决的问题。

**SillyTavern 1.19.0 的时间相关实现：**

- 时间宏（`public/scripts/macros/definitions/time-macros.js`）：`{{isodate}}` `{{isotime}}` `{{weekday}}` `{{date}}` `{{time}}` `{{idleDuration}}` 等。
  `idleDuration`（`getTimeSinceLastMessage`）跳过最新一条非系统消息，取再往前最近一条用户消息到现在的时长（moment `humanize`）。
  对方连发三条时它算出来是「几秒」，正是方案 5.3 说的「把离开三天覆盖成刚刚」。
- 摘要的「After Main Prompt」位置：`openai.js:1389` 取 `1_memory`，`:1145` 把 IN_PROMPT 换成 `end`，`:1265` 插在 main 之后。

**方案的三条记忆路线对应到运行时：**

| 路线 | 方案里的组成 | 放到本项目 |
| --- | --- | --- |
| A | ST Summarize + Vector Storage | 都是 ST 前端扩展，运行时用不了；可以照它的做法（方案 6.2 关系状态、7.1 摘要提示词）自己实现 |
| B | Smart Memory | ST 浏览器扩展，用不了 |
| C | Hindsight 服务 + 适配层 | 独立服务，运行时可以直接调；要多跑 Hindsight、PostgreSQL、embedding 三个服务 |

方案 2.2 的建议是先比较 A 与 B，只有明确的跨 chat、跨客户端、来源追踪或隔离需求时再评估 C。
本项目每位联系人本来只有一条连续的聊天记录，没有 ST「换 chat 记忆断开」的问题。

**10-04 的探索分支**（`research/deep-study`，最后提交 `7b254e6`，已删除）试过 A 的自建版和 C。审查结论：

- C 的客户端有 4 处与官方 OpenAPI 不符，错误又被吞掉：建库与改配置的接口不存在（mission 从未生效）、`async` 和 `tags` 放错层级
  （写入变成同步、1.5 秒必超时；记忆没有标签）、每次用新的 `document_id` 重写全部历史（重复提取）。
- 本地 embedding 是哈希向量，不是语义检索。
- A 的自建版每次把全部聊天记录交给主模型摘要，没有时间、截止位置和串行控制。
- 时间锚点精确到分钟、放在整段聊天记录之前，每次请求都让后面的前缀缓存失效。

没有可以直接复用的代码，教训体现在下面的决策里。

## 决策

### 1. 按方案 2.1 的处理顺序补齐，分四步

| 步骤 | 内容 | 方案章节 |
| --- | --- | --- |
| 1. 时间 | 决策 2 | 5.3 |
| 2. 角色表达 | 并入 M2 生成分档角色卡：示例对话（`mes_example`，按 ST 的格式和挤出规则实现）、简短的末尾指令。每档单独写，不放所有档位共用的常量 | 3.3、3.4、4.3 |
| 3. 消息调度 | 连发合并（静默约 2 秒、最长等约 6 秒）；拆条发送时每条之前检查新消息，过时的剩余部分不发 | 5.2 |
| 4. 长期记忆 | 决策 3（Hindsight） | 6、9、10、11 |

动作描写、空头承诺先靠提示词和示例解决（方案 4.3），不加按关键词删括号的正则；出口检查仍在 M4。

### 2. 时间：运行时自己算，放在最新消息旁边

- 每次生成时算出：当前日期、星期、时间（本机时区）；这一组消息（上次回复之后对方发的几条）第一条的时间；
  这一组之前双方最后一条消息的时间，以及间隔。连发时间隔按第一条算，不按最后一条。
- 写成一条 system 消息，放在聊天记录之后、末尾指令之前（相当于 ST 作者注放在聊天中 depth 0）。
  不放在聊天记录前面：每次都变的内容放在前面，后面整段聊天记录就用不上前缀缓存（方案 5.3 末段）。
- 另外实现上面列出的 ST 时间宏，行为照 `time-macros.js`，只为角色卡里用到时和 ST 一致。运行时的时间块不依赖 `idleDuration`。
- 作息、课表是角色设定，不写进代码，留到 M3 作息另定。

### 3. 长期记忆：接 Hindsight（方案路线 C），按方案第 9、10 节

- 部署：Hindsight 服务装在 `runtime/`，固定版本，来源与核对过程记在 `docs/hindsight.md`（同 `docs/napcat.md` 的做法），只监听 127.0.0.1。
  embedding 必须是真正的语义模型，接入前先用方案 7.2 末段的中文用例验证（昵称、独特绰号、否定句、相近事件、日期）。
  启动脚本只在配置里启用了记忆时才拉起这些服务。
- 请求对照所装版本的官方 OpenAPI 写，并有测试核对请求形状；调用失败要记日志，不吞掉错误，也不在失败后打印成功。
- bank：每位联系人一个，ID 不含原始 QQ 号（方案 9.3，用稳定哈希）。实现时改为每位联系人每个档位一个（ADR 0003「实现时的调整」第 3 条）。建 bank 时写入方案 9.4 的三个 mission。
- 写入（retain）以聊天片段为单位：一段对话安静约 45 分钟（方案 5.2），或这一段还没写入的部分快被挤出上下文时，
  把这一段聊天记录（说话人、时间、QQ 消息 id）作为一个文档写入。`document_id` 固定为片段 id，同一片段再写时整段替换（方案 9.7）；
  带 `timestamp`；后台异步，失败的片段下次重试。只写聊天记录里的消息，发出去的才在里面。
- 召回（recall）：每次生成前用最近几条消息组成查询（方案 9.5：要带上这次的话题和指代），限时；超时或出错就不注入，不拖住回复。
  召回内容每次都变，放在聊天记录之后（和时间块一起）；没有相关内容就不注入（方案 6.3 第 7 条）。
- 关系概况：用 Mental Model 保存「当前关系概况」（方案 9.6），定期读取，放在 main 之后（同 ST 摘要的「After Main Prompt」）。
  首版不在每条消息前调用 reflect（方案 9.8）。
- 还没写入 Hindsight 的部分由上下文里的聊天记录原文承接（方案 9.5 末段、T19）。
- 原始聊天记录仍是依据，Hindsight 里的是派生数据。Hindsight 不可用时 bot 照常回复，只是没有长期记忆。

### 4. 验收用方案第 13 节

- 沿用方案的 T01–T24 编号和通过条件，运行时不适用的标出来（T15 换 ST chat、T19 Hindsight 当前块）。
- 每步完成时按方案 13.1 记录：输入、平台时间、实际提示词（`last-prompt.json`）、模型原文、清理后正文、发送结果。
- 单元测试只证明代码行为。口吻、自然度、时间承接这类用例（T01–T06、T10–T14）必须在 QQ 上实测，roadmap 写明实测时间和结果，不用单元测试代替。
  （2026-10-04 由 [ADR 0005](0005-scenario-simulation.md) 修改：这些用例先在模拟器里用真模型跑，QQ 实测只做冒烟和只有 NapCat 能走到的路径。）

## 备选方案

| 方案 | 不选的原因 |
| --- | --- |
| 自建：每人一份滚动摘要 + 未完成事项 | 不用多跑服务，但事实提取、按时间和语义找回、观察整合、来源追溯都要自己做，摘要质量也要自己维护 |
| 时间写进角色卡（scenario 里用 ST 宏） | 位置在提示词前部，每分钟都变，破坏缓存；`idleDuration` 遇到连发语义不对 |
| 按关键词删动作括号 | 误伤正常补充（「（拍照的那家店）」），方案 4.3 不建议；应改提示词和示例 |

## 后果

- 时间块和记忆块在 ST 里没有直接对应（ST 里要靠作者注和摘要扩展），ST 试聊的提示词会和运行时不同；差异可以在 `last-prompt.json` 里看到。
- 多三个常驻服务（Hindsight API、PostgreSQL、embedding），启动和排错都更复杂。
- 每个片段写入时 Hindsight 要调用模型提取事实，有额外的模型费用；召回让每次回复多一次本地请求。

## 确认记录（2026-10-04）

1. 记忆路线：Hindsight。草案推荐的是自建，用户选了 Hindsight。
2. 顺序：时间 → M2（含角色表达）→ 消息调度 → 长期记忆。
3. 探索分支里有效的角色修正（不再怼人、不乱许诺）按同样的效果重写后先合并（`cad4a27`），不照搬原文。
