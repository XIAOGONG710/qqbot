# ADR 0137：逐条事实检查（配置 `factCheck`：off / log / fix，默认 off）

- 状态：**已实现，未上线**（2026-10-24）。上线 = 换代码重启 + `koishi.yml` 里加 `factCheck: log`（先只查只记）或 `factCheck: fix`；回滚 = 改回 `off`（或去掉这一行）重启
- 日期：2026-10-24
- 关联：[ADR 0006](0006-exit-check.md)（出口检查）、[ADR 0108](0108-proactive-opener.md)、[ADR 0133](0133-proactive-lead.md)、[ADR 0135](0135-proactive-openers.md)（主动消息别添事实里没有的小动作）
- 来源：2026-10-24 对照麦麦（MaiBot）等相似项目后用户说「123都做」；这是第 2 条（逐条事实检查，借 ACL 2025 的原子级人设一致性评估：[arXiv 2506.19352](https://arxiv.org/pdf/2506.19352)）

## 问题（有数据）

她最容易露馅的不是语气，是**编**：看着很自然的新事实。这一周读出来的几类：

- 土豆（楼下的流浪猫）的举动：事实里只有“土豆今天没下楼 / 昨天喂过”，她写「蹲在楼道口等我，一见我撒腿就跑，跑两步又回头看我」；
- 和她此刻的状态对不上：状态是在逛淘宝，她写「放下手机」；
- 凭空的人和事：「你口味那么杂」（记忆关着、没聊过）、没提过的室友的举动、没提过的课表。

出口检查（`exit-check.ts`）只拦得住几类固定的毛病（做不到的事、禁用词、助手腔、照抄语音图片的写法……），拦不住这种“看着很自然的新事实”；ADR 0108 / 0133 / 0135 在提示词里写了“事实只能用上面写了的”，模型多半听，但不是每次。所以在出口再查一遍。

## 做了什么

- `fact-check.ts`：回复发出去之前，让模型当**审稿员**（一次额外的小调用，温度 0，只输出一个 JSON 数组）。给它：设定和这一轮的事实（拼提示词时 ST 后处理**之前**的 system 部分——后处理会把后面的 system 改成 user，分不出哪些是事实）、聊天记录、她准备发的回复。要求它把回复拆成关于**她自己或她身边世界**的一条条具体说法（在做什么 / 刚做了什么 / 手上和身体的动作、吃了什么、去了哪、见了谁、谁说了什么、猫和东西的具体行为、发生了什么事、具体数字和时间），到设定、事实、聊天里找依据，只列两种：`contradicts`（和写的对不上）、`invented`（完全没提过的具体新事实）；感受、想法、看法、玩笑、对他的提问和回应、聊天里已经说过的事、泛泛的常识、含糊的口头话都不列，拿不准不列。
- 解析（`parseClaims`）：容忍代码块和前后废话；**回复里照抄不出来的片段当没说**（防止审稿员瞎编）；类型不对、太短的丢掉；最多采信 4 条。
- 三档：`off` 不查；`log` 只查、只记日志，回复照发（敏感调试关着时日志只记条数和字数，不记原话；要看原话就用 `QQBOT_SENSITIVE_LOGS=15m` 开一会儿）——**先看误报多不多**；`fix` 有问题就在提示词末尾加说明（「…是上面事实里没有的 / 和上面写的事实对不上；你只能说上面写了的事实，或者说你自己的感觉和想法；别添上面没写的小动作、小场景、别人的举动」）重写一次，重写出来的再查一次，还有就把含这几句的行删掉（删完一行不剩就照发重写的）。
- 位置：`contact.ts` 的 `review` 里**先于**出口检查——重写出来的话还要过出口检查这一关。聊天回复和主动消息都走；危机回合不查（不拖慢、不改危机回复）；固定说法（`allowRepeat`，B 站私信之后的提醒）不查；不到 6 个字、只有表情包 / 照片指令行的不查。
- **绝不挡回复**：审稿超时（25 秒）、模型不可用、解析不出，一律照发并记一行日志。
- 模拟器：场景字段 `factCheck`、命令行 `--fact off|log|fix`；报告里每次检查多一行「事实检查（没问题 / 重写后过了 / …）：矛盾「…」（理由）」；「用量小计」另外列出审稿次数和输入量。

## 数据

真模型模拟（`--fact fix`，6 个场景 × 2 次：主动小事 / 喂猫 / 吃的照片 / 睡前早安 / 日常闲聊 12 句 / 意见知识倾诉 12 句；67 次生成 + 48 次审稿，约 0.36 + 0.20 百万输入 token）：

| | 次数 | |
|---|---|---|
| 审稿没挑出问题 | 45 | 通读她这些回复，没发现漏掉的明显编造 |
| 挑出问题 | 3 | 「白拿猫粮下去」（事实里只有土豆今天下雨没下楼、昨天喂过——编的动作）；「明天就上午一节课」（提示词里没有课表——编的）；「没玩了没玩了 / 就瞄一眼」（状态是在逛淘宝，和“没玩”对不上） |
| 重写后再查 | 3/3 过 | 例：「今天下雨没下楼，土豆都见不着了」「被你抓到了 / 在逛淘宝 / 这个不算玩」 |

召回探针（拿一份真实提示词当事实，8 句手写的编造 + 8 句没问题的，温度 0）：编造的抓到 **6/8**（漏了「下午我去操场跑了三圈」「明天上午我有高数课」），没问题的误报 **0/8**。审稿一次约 1.2–3.3 秒（5 次平均 1.7 秒），输入约 4–5 千 token（和聊天本身的提示词差不多大）；打字时间本来就要等，多出来的这几秒大多落在里面。

样本小：48 次审稿只挑出 3 条，不能说“编造的比例就是 6%”；召回 6/8 也只是 8 句手写的。线上建议先开 `log` 看一两天条数，再改 `fix`。

## 没做 / 要注意

- 费用：每个会被查的回复多一次输入约 4–5 千 token 的调用（线上聊天一天几十轮，约 +0.15–0.25 百万 token / 天）；`log` 和 `fix` 一样花这一笔（`fix` 在被挑出来的那几轮再多一次重写 + 一次再查）。
- 审稿员和说话的是同一个模型：它自己也会错过“看着合理”的编造（召回 6/8）；它看不到“事实里没写、但其实是真的”的东西（例如不在提示词里的设定），所以可能把真的当没依据——`fix` 档下这会让她少说一点细节，不会说错话。
- 只查文字行，表情包 / 照片指令不查。
- 不查“他说过的话她记错了”这一类（需要对照聊天记录逐句，成本更高）；也不查语气。
- 单元测试：`fact-check.test.ts`（拼提示词、解析、三档、审稿出错 / 超时、模拟器里开 / 关 / 危机回合）。
