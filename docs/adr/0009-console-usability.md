# ADR 0009：控制台易用性——整理插件表单（A），角色资料在控制台里改（B，定方向）

- 状态：已采纳（2026-10-05：待定问题与用户确认，见文末「确认记录」；试验后的调整见「试验结果」，A2 名单用卡片由用户看截图选定）
- 日期：2026-10-05
- 关联：[ADR 0008](0008-koishi-runtime.md) 决策 4（配置分三层）、需求 8（运行配置在控制台改）；[ADR 0003](0003-contact-tiers.md)（档位与隐私）

## 背景

10-05 切到 Koishi 后，用户实际用下来觉得 qqbot 插件的配置界面不好用：名单看不全，参数看不出实际值，思考开关要手写 JSON，
写错了也看不出来。另外，世界书、人设、作息不能在页面上改。

### 取证（2026-10-05）

用 `scripts/start-koishi.ps1` 起了一个临时实例（`runtime/koishi-ui-tmp`，端口 5141）。它连的是假 NapCat 和假模型，联系人是虚构的。
截图留在会话的 scratchpad 里，不入库。

| 问题 | 界面上看到的 |
| --- | --- |
| 名单 | `role('table')` 四列挤在约 780px 宽的表单里。persona 列约 150px，而且是单行框（表格里 `textarea` 不起作用），长人设只能看到前 9 个字。档位列显示「boyfri…」「class…」，下拉写的是「boyfriend（男朋友）」。QQ 列是带 −/+ 的数字步进框 |
| 数值参数 | 没写默认值的项（maxTokens、两个超时、世界书 3 个数值、记忆 2 个超时、bankPrefix）是空框，实际值只能看说明里的「留空为 X」。世界书 3 个开关没有默认值，显示成灰色的「未定」，看不出开还是关 |
| 写错配置 | extraBody 写成坏 JSON 保存后，控制台弹绿色的「配置已重载」，侧栏仍是绿点（刷新页面也是）。实际上插件已经停了：注入的消息没人接，也没记进聊天记录。唯一的痕迹是插件页「运行日志」里一条带 20 行调用栈的 [E]。必填的 `llm.model` 清空后表单不标红，照样能保存，结果也一样。改对再保存后，停掉期间来的消息由补回接上 |
| 布局 | 每项的标题是英文键名（`contacts`、`llm.baseUrl`、`prompt.worldInfo.depth`），中文说明是下面的小字。记忆关着时细项照样显示。世界书 6 项、`characterCard`、`dataDir` 和名单在同一页平铺。顶部还有一块 Koishi 通用的「过滤器设置」，对我们没用 |
| 生效了没 | 插件页顶部有「运行日志」框，换档提示（「QQ … 的档位从 classmate 变成 known」）、「09:59:17 看到」都能看到。但框只显示约 10 行，上一次出错的调用栈会把新内容顶出去 |
| QQ 号 | 只能手填 |
| 运行状态 | 除了运行日志，看不到谁有回复在等、NapCat 和 Hindsight 连没连上 |
| 思考 | 开不开、强度多少，都要在 extraBody 里手写 JSON |
| 角色资料 | 世界书、人设、作息、课表都不能在页面上改 |

查到的机制（Koishi 4.18.11、控制台 5.30.11、cordis 3.18.1、schemastery 3.18.0）：

- 写错配置时为什么是绿点：插件在 `apply` 里抛错，cordis 只把插件主体（MainScope）标成失败；控制台显示的是实例（ForkScope）的状态，实例仍是 ACTIVE。
  反过来，保存时 Schema 校验出错，出错的是实例的 `update`，实例会被标成失败（`@cordisjs/core` `ForkScope.update`）。
- 表单的标题固定是键名，说明按 Markdown 渲染。下拉选项显示的是选项的 `description`，没有才显示值。
  字符串的 `.pattern()` 不匹配时，表单会提示。`.collapse()` 可以折叠。插件导出 `usage`（Markdown，显示在插件页顶部）、`filter = false`（去掉「过滤器设置」），控制台都会读。
- 用 `.default()` 声明的默认值会显示在表单里，但保存时不写进 `koishi.yml`（loader 写文件前做了 `schema.simplify`）。
- `Schema.dynamic(name)` 加 `ctx.schema.set(name, schema)`：控制台收到 `internal/schema` 后把新 schema 推给前端，所以可以在运行时生成下拉选项（例如好友列表）。
- 插件用 `ctx.scope.update(新配置)` 改自己的配置时，loader 会按 Schema 把它写回 `koishi.yml`（`internal/before-update`）。迁移旧写法可以靠这个，试验里再确认。
- 控制台的插件列表只扫描实例目录往上的 `node_modules`。临时实例放在仓库外时，插件页显示「此插件尚未安装」，所以临时实例要放在仓库的 `runtime/` 下。
- DeepSeek 的思考参数（[Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)、[Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)，10-05 核对）：
  - `thinking: {type: enabled | disabled}` 默认开启；`reasoning_effort` 可选 `low` / `high` / `max`，默认 `high`。`none` 等于关，`minimal`→`low`，`medium`、`xhigh`→`high`。
  - 思考时 `temperature`、`presence_penalty`、`frequency_penalty` 不生效（不报错），`max_tokens` 包含思考过程。

## 需求

1. 名单：每个人的 QQ、称呼、档位（中文）、persona 全文都能一眼看清、方便改。加人时从小号的好友列表里选，选不到时能手填。
2. 表单显示实际在用的值，不用读说明。默认值只有一份（`config.ts`），由测试保证两边一致。
3. 思考：开关和强度用控件选。其余额外参数留一个 JSON 框。
4. 常用项放前面，平时不动的项折叠；长期记忆关着时不显示细项。
5. 保存后看得出生没生效：配置错了，控制台要明显标成失败，错误用一句话说清是哪一项，不带调用栈。能在保存前拦下的，在表单上就标出来。
6. 在控制台里看得到换档提示、正在等的回复（几点看到）、NapCat 和 Hindsight 连没连上。
7. 世界书、人设、作息、课表能在控制台里改，改完自动生效。
8. 旧的 `runtime/koishi/koishi.yml` 照常读。新旧写法不同的地方由插件自动迁移，不用手改。
9. 不改 Koishi 和控制台的源码。`config.json`（`main.ts` 路线）不受影响：同样的配置经 Schema 和经 `config.json`，解析出来完全一样。
10. 角色资料仍受档位隐私保护（ADR 0003）：低档位的卡里不能出现高档位才知道的事，禁用词检查照旧。

需求 1–5、8、9 是 A 部分，只改插件的 Schema 和接线，不写前端。需求 7、10 是 B 部分：表单只能改 `koishi.yml` 里的插件配置，
改不了仓库里的角色资料文件，所以要在页面上改就得写一个页面。需求 6 的完整版（状态面板）也放进 B 的页面（确认记录第 4 条）。
B 部分这里只定方向，细节另写 ADR 0010。

## A：整理插件表单（只改 Schema）

### A1. 文字和档位

- 键名不改（一改旧的 `koishi.yml` 就读不了），说明改成中文名放在前面，例如「**称呼**：提示词里的 {{user}}」。
- 档位下拉显示「男朋友」「闺蜜」「女生熟人」「熟人」「同学」「陌生人」，存的值不变。
- 导出 `filter = false`，去掉「过滤器设置」。用 `usage` 在页面顶部写几行说明：保存会重启插件、换档提示看运行日志、怎么改人设。

### A2. 名单

- 排法（用户看试验截图选了 (a)）：
  - (a) 每人一张卡片：QQ、称呼、档位各占一行，persona 用多行框占一整行。存的形状不变，不用迁移。
  - (b) 表格只留 QQ / 称呼 / 档位三列，persona 另放。存的形状变了，要迁移；QQ 号也只能手填（试验结果第 1 条）。
- QQ 号从好友列表选：插件连上 NapCat 后调 `get_friend_list`，用 `ctx.root.schema.set('qqbot.friends', …)` 生成选项，显示成「备注（昵称）QQ 号」。
  挂在根上下文上，插件失败或重启时下拉仍在，显示上一次拉到的列表（试验结果第 5 条）。
  Koishi 启动后还没拉到过好友列表时（NapCat 没连上），退回手填数字框。名单里已有但不在好友列表里的号照样保留，标上「不是好友」。

### A3. 默认值

- `config.ts` 导出默认值常量（temperature 1、maxTokens 300、timeoutMs 120000、maxContext 8192、世界书 6 项、记忆 3 项），
  `parseAppConfig` 和插件 Schema 的 `.default()` 都用它，测试断言两边一致。
- 世界书的 3 个开关有了默认值，不再显示「未定」。
- 等于默认值的项不会写进 `koishi.yml`（见取证）：以后改默认值，没手动设过的项会跟着变，和现在一样。

### A4. 思考和额外参数

- 新增 `llm.thinking`，选项为：不设置（用接口默认）/ 关 / 低 / 高 / 最高。
  - 关 → `thinking: {type: 'disabled'}`（现在用的就是这个）；低 / 高 / 最高 → `thinking: {type: 'enabled'}` 加 `reasoning_effort: low / high / max`。
  - 说明里写清两点：开思考后温度不生效；回复长度上限包含思考过程，所以要调大。
- `extraBody` 键名不变，说明改成「其他参数（JSON）」。JSON 写错时保存就失败（A6）。
- 冲突和迁移：
  - 控件设了值，JSON 里又写了 `thinking` / `reasoning_effort`，按配置错误处理。
  - 旧配置（控件没设）JSON 里的这两个键，插件第一次加载时搬到控件上，用 `ctx.scope.update` 写回 `koishi.yml`。
    值对不上任何选项的，原样留在 JSON 里。
- 只有插件做这个转换。`config.json` 照旧写 `extraBody`，`parseAppConfig` 不变。

### A5. 分组和折叠

| 组 | 内容 | 默认 |
| --- | --- | --- |
| 联系人 | 名单、名单外好友、作息开关 | 展开 |
| 模型 | 地址、模型名、思考、温度、回复长度上限；排在最后、说明里标「一般不用改」的：其他参数（JSON）、Prompt Post-Processing、请求超时 | 展开 |
| 长期记忆 | 开关；开着时显示地址、两个超时、bank 前缀 | 展开 |
| 高级（一般不用改） | 提示词（上下文上限、示例常驻、世界书 6 项）、角色卡路径、数据目录 | 提示词和其中的世界书各自折叠 |

- 存的形状不变（仍是 `llm` / `prompt` / `memory` 几个对象），只改显示的位置。
- 每个对象只放在一个组里。试验时把 `llm` 拆到两组里显示，能显示，但实现时发现 `schema.simplify` 会丢数据（试验结果第 4 条的更正）。
  所以模型的高级参数留在「模型」组的最后，没有折叠。
- 顶层分组不能整组折叠，只有嵌套对象能折叠。所以「高级」组里 `prompt`（含 `worldInfo`）折叠，`characterCard`、`dataDir` 平铺。
- 长期记忆的条件显示仿照 `plugin-auth` 的写法：`Schema.union`，`enabled: true` 时才多出细项。存的形状不变。

### A6. 保存后看得出生没生效

- 配置错时，让控制台把插件标成失败：插件声明 `reusable`，`apply` 改在实例里运行，抛错时实例就失败（试验结果第 2 条）。
  另一种做法是把校验挪进 Schema（`Schema.transform`），但被它包住的字段在表单里不显示输入框，不能用。
- 错误只写一句，不带调用栈，例如「配置有误：其他参数（llm.extraBody）不是合法的 JSON，第 1 行第 32 列」。
- 能在表单上提前标出的项提前标出：字符串格式用 `pattern`，必填项不能是空串。
- 改对之前那段时间来的消息，改对后由补回接上（取证时验证过，补回只取最近 20 条）。

### A7. 运行状态

换档提示、正在等的回复、NapCat / Hindsight 的连接状态放进 B 的页面（确认记录第 4 条）。A 里只做 A6，换档提示照旧写在运行日志里。

## B：角色资料在控制台里改（定方向，细节写 ADR 0010）

现在的数据流：`legacy/`（旧项目原件，逐字节不改）+ `tiers.toml`（手写：每段给哪些档位、改写、各档说话方式、示例对话、禁用词）
→ 转换器 `character-tools` → `st/` 下每档一张卡、一本世界书 → 插件监听 `st/`，文件变了自动重读。
作息和课表来自 `legacy/schedule.toml`、`timetable.toml` 加 `tiers.toml` 的 `[schedule]`，转换后写进卡的 `extensions.qqbot.schedule`。

不管选哪条路，保存流程都一样：

1. 页面上改；
2. 保存时跑转换器和档位检查（禁用词、可见性，与 `character-tools` 的测试同一套规则）；
3. 检查不过就不写，并指出是哪一档的哪一句；
4. 检查通过就写文件，插件按现有的卡文件监听自动重读。

改动写进仓库里的文件，提交照旧由我来做，推送前问用户。

不放进 `koishi.yml`：那个文件不入库，角色资料放进去就脱离了 git 和档位检查。

| 方向 | 做法 | 代价 |
| --- | --- | --- |
| **页面 + 新的可编辑资料（倾向）** | `legacy/` 留作原件不动。用 `legacy/` 加 `tiers.toml` 一次性生成一份可编辑的资料（入库），之后转换器只读它；控制台里加一个「林梦瑶」页面，直接读写它 | 要写前端（见后果）。`tiers.toml` 里解释「为什么这样写」的注释要搬成字段里的备注 |
| 页面 + 三层叠加 | `legacy/`、`tiers.toml` 都不动，页面的改动另写一个文件，转换时最后叠上去 | 删掉或新增一个场景、一门课要特殊表示，三层越叠越难看懂 |
| SillyTavern | 用已装好的 SillyTavern 改卡和世界书 | 改的是某一档的生成文件，跳过了档位过滤，转换器加 `--force` 会覆盖；作息、课表不在 SillyTavern 里 |

页面本身：Koishi 的控制台页面是 Vue 组件（`@koishijs/client`，AGPL-3.0）。有两种写法，在 ADR 0010 里试：

- 用 vite 构建：多一套前端构建和 AGPL 的开发依赖；
- 不构建：直接写 ES 模块，用控制台运行时提供的 vue / element-plus。不多依赖，但组件要用 `h()` 手写。

页面在控制台登录之后才能用，控制台只监听本机。

| 2 | 配置错时标成失败 | `reusable` 和 `Schema.transform` 各试一次，记下控制台显示什么、错误信息是否只有一句；能用的那种，正常配置的行为不变 |

### 试验结果（2026-10-05）

两个一次性的试验插件，试完已删除，没有入库：A 用卡片、`reusable`；B 用三列表格、不用 `reusable`、用 `Schema.transform` 校验。
截图留在会话的 scratchpad 里。

| # | 结果 | 对决策的影响 |
| --- | --- | --- |
| 1 | 卡片：persona 整行多行框，能看全；好友下拉显示「备注（昵称）QQ 号」；不在好友列表里的号显示「29999（不是好友）」。表格里只要有一列是动态下拉，控制台就把整张表退回卡片：「从好友列表选」和「表格」只能二选一。三列表格（QQ 手填）一人一行，persona 另放一个以 QQ 号为键的列表 | 用户选卡片（A2 (a)），存的形状不变 |
| 2 | `reusable`：`apply` 抛错时侧栏变红点（`status-light failed`），改对再保存变回绿点。错误对象的 `stack` 设成和 `message` 一样时，运行日志里只有一行。`Schema.transform` 包住的字段在表单里不显示输入框，不能用 | A6 用 `reusable` |
| 3 | 插件在 `apply` 里同步调 `ctx.scope.update` 时 `koishi.yml` 不变：首次加载时 loader 还没登记这个实例。延后一拍（`ctx.setTimeout(…, 0)`）再调，`reusable` 和普通插件都会写回，插件只重启一次。写回时等于默认值的项会被去掉（例如 `extraBody: '{}'`） | A4 的迁移延后一拍执行 |
| 4 | 同一个嵌套对象（`llm`）拆到两组里，表单能显示，存的形状不变。**实现时更正**：`schema.simplify` 对 intersect 的各组结果做浅合并（`Object.assign`），后一组的 `llm` 整个盖掉前一组的；后一组有非默认值（例如 `promptPostProcessing: semi`）时，`baseUrl`、`model`、`thinking` 都会丢。loader 写回插件自己改的配置、控制台的「按 JSON 编辑」都用它。试验时后一组的值都等于默认值，所以没暴露。顶层分组上的 `.collapse()` 不起作用；嵌套对象上的 `.collapse()` 可以，显示成「展开以编辑」，两层（`prompt` → `worldInfo`）都可以。记忆的条件显示可用 | 每个对象只放一个组；A5 的「高级」组不能整组折叠，`prompt` 折叠，`characterCard`、`dataDir` 平铺。测试加一条：各种配置经 `simplify` 写回再读出来不变 |
| 5 | 好友列表每 15 秒刷新一次，没保存的修改不丢。动态 schema 的说明会顶替字段自己的说明。插件失败或重启时，插件上下文注册的动态 schema 会被一起卸掉，QQ 号那一栏变成空白；改用 `ctx.root.schema.set` 注册后，失败时下拉仍在 | 字段说明写在动态 schema 上；好友列表挂在根上下文上，保留上一次拉到的列表 |

`reusable` 的代价见后果一节。

## 第 2 步：实现（小步提交，每步能运行、测试通过）

1. `config.ts` 导出默认值常量，行为不变。
2. Schema：中文说明、档位中文、默认值、去掉过滤器、`usage`；用旧 `koishi.yml` 的写法做测试数据，确认仍能读。
3. 分组折叠、记忆的条件显示。
4. 思考控件、冲突检查、迁移。
5. 名单排法和好友下拉。
6. 配置错时标成失败，错误只写一句。

## 备选方案

| 方案 | 不选的原因 |
| --- | --- |
| 把键名改成中文，让标题变成中文 | 旧 `koishi.yml` 读不了，要迁移所有键，`config.json` 和 `koishi.yml` 也不再同形；说明里把中文名放前面效果接近 |
| extraBody 改成键值对（`Schema.dict`） | 值是任意类型，嵌套对象（`thinking: {type}`）在表单里没法好好编辑；常用的已经做成控件，剩下的用 JSON 更直接 |
| 在 `apply` 里吞掉配置错误、带着上一次的配置继续跑 | 控制台显示的和实际在跑的不一致，比标成失败更难察觉 |
| 角色资料放进 `koishi.yml`，用 Schema 表单改 | `koishi.yml` 不入库，资料脱离 git 和档位检查；一百多个场景、十几门课放进表单也没法用 |

## 后果

- A 部分只动插件和 `config.ts` 的默认值，`main.ts` 路线行为不变。
- `koishi.yml` 的写法基本不变，唯一的迁移是思考参数，由插件自动完成。
- 选 `reusable` 的话，控制台会允许给插件「再加一个实例」；第二个实例会被单实例锁挡住，起不来。
- B 部分会带来前端代码，可能还有 AGPL 的开发依赖；角色资料的来源从 `legacy/` + `tiers.toml` 换成新的可编辑资料，ADR 0003 的数据流要跟着改。这些在 ADR 0010 里定。
