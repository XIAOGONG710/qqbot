# ADR 0065：「新事实顶掉旧事实」小测试（先量再决）

- 状态：**提议**（2026-10-12 用户在 `options.md` 里选了 C1；这是一次**实验**，不改产品代码）
- 日期：2026-10-12
- 关联：[ADR 0012](0012-hindsight-tuning.md)（写入说明：否定和更正各单列一条；10-09 的离线日期审计）、[ADR 0017](0017-long-term-memory-like-a-person.md)（临时 bank 做验证的做法）、
  [ADR 0018](0018-memory-fades-and-promises.md)（变淡、一提就想起）、[ADR 0039](0039-restart-consistency.md)、`docs/memory-editing.md`
- 调研依据：`exchange` 分支 `exchange/research/2026-10-companion-practice/block-c.md`、`options.md`

## 背景

C 块的结论：我们的「淡化 + 一提就想起」比读到的所有项目都贴近目标，但有一个缺口**没验证**——**同一个会变的属性（工作、住处、状态）说过两个版本时，她会用哪一个**。

- ADR 0018 的变淡按「最后一次被提起的日子」算，不按「这个事实是否已经过期」算：「换了工作」之后，旧版本只要最近被提过，仍可能被召回。
- ADR 0012 / 0017 / 0018 和 `docs/memory-editing.md` 里**没有**「新事实让旧事实失效」这一条；Hindsight 整合时怎么处理矛盾，我没查，也没有测过。
- 别人的同类问题有记录：mem0 #4956（v3 只增不改，换工作的新旧事实并存，排序里没有时间信号；2026-04 开，至今 open，无维护者回复）。评测界把它叫「知识更新」（LongMemEval，ICLR 2025 的五种能力之一）。
- 只有 10-09 的一次离线审计查出过 3 条日期错误，那是**日期换算**问题，不是**新旧事实**问题。

所以先量，不先做：量出来现状够用，就不加有效期层（调研里的 C2）；不够用再另开 ADR。

## 决策

1. **新增模拟器场景 `memory-update.json`**（照 `memory-fading.json`、`memory-diary.json` 的格式：`start`、`steps` 里 `say` / `advance` / `memory` / `check`），**全部是虚构属性，不用任何真实人的信息**。三个变体，各自独立跑：
   - **A 工作**：第 1 天他说「我在某某公司实习」；第 4 天说「我换到另一家了」；第 8 天问「你还记得我在哪实习吗」。
   - **B 住处**：第 1 天他说「我住 3 号楼」；第 5 天说「我搬到 7 号楼了」；第 9 天问「你知道我现在住哪吗」。
   - **C 明确更正**：第 1 天他说「我不吃香菜」；第 3 天说「其实我现在能吃了，以前是我记错了」；第 7 天问「我吃不吃香菜」。
   - **对照**：每个变体再配一条**只说过一次**的同类属性，确认「没被顶掉的」她还记得。
2. **每个变体跑 3 次**（真模型，`--parallel 1`，按 0058 验证时用户允许的口径：纯虚构模拟对话可以发给模型）。
3. **度量**（每次一格，事先写定）：回答是 **新版 / 旧版 / 新旧并说（含混）/ 不记得**；同时记下召回里新旧条目是否**同时出现**（从日志 `召回长期记忆 N 条` 和模拟器报告里的条目取）。
4. **判据（事先定，避免事后挑）**——Claude 提议的数字，用户可以改：
   - 9 次里「答新版」≥ 8 次，且「答旧版」≤ 1 次 → **现状够用，不做有效期层**，把结果写进 ADR 0018 的验证节；
   - 否则 → 另开 ADR 做有效期层（调研 C2，参考 Graphiti 的 `invalid_at`：旧事实保留、标失效、召回时降权）。
5. **运行条件**：
   - 带记忆的模拟用 **`sim-` 前缀的临时 bank**，跑完删掉，事后查一次没有残留（0017 的做法）；
   - **复用线上正在跑的 Hindsight 服务，不另起第二个**；这台虚拟机 6 GB，10-10 记过「Hindsight 约 1.7 GB，ChatGPT app 约 1.6 GB，带记忆的模拟放不下」，所以**跑之前先看可用内存**，不够就等或挑线上空闲的窗口——这一步需要用户同意，Claude 不自己停线上服务；用户已定不加内存，不再提；
   - 若实在放不下，退而求其次是假 Hindsight 只验场景和度量脚本，但**这样测不到真实整合行为，结论不算数**。
6. **产出**：一份 `docs/reports/2026-10-xx-knowledge-update.md`，写 9 次的原始判定表、召回里新旧同时出现的次数、按判据的结论；不改产品代码，不改线上数据。

## 实现步骤

1. 写场景 JSON 和度量检查（`check` 里加「答新版 / 旧版」的字面匹配，匹配规则事先写在场景里）。
2. 看内存、选窗口（问用户）。
3. 跑 9 次 + 对照，保存报告。
4. 按判据写结论；需要 C2 就另开 ADR。

## 验证

- 场景本身：用假模型走一遍，确认检查能区分新版 / 旧版 / 含混。
- 结果：9 次判定表原样放进报告，不做事后筛选。

## 备选方案

| 方案 | 不选的原因 |
| --- | --- |
| 直接做有效期层（C2）| 还不知道现状是不是问题；会在 Hindsight 之外加一层，矛盾仍靠 LLM 判，会误判 |
| 只读 Hindsight 文档判断 | 文档不等于行为；0017 / 0018 都是靠真模型验证 |
| 在线上真实联系人身上观察 | 样本小、不可控，还会用到真实的人 |

## 后果

- 不改产品，不改线上数据；成本是一次带记忆模拟的时间和那段内存窗口。
- 结果会写进 ADR 0018 的验证，供以后对照。
