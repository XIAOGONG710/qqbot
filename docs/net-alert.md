# 外网断了，用她的 QQ 告诉你

- 日期：2026-10-18（Claude）。状态：**代码和测试做完，默认关，线上没动**（分支 `claude/net-alert`）。
- 为什么：10-14 到 10-18 好几次，虚拟机连不上模型（回复、主动消息、看图全失败）要很久才被发现；10-16 / 10-17 一次断了 20 小时。心跳守望只往本机写 `ALERT.txt`，没人看。
  这几次 NapCat 到 QQ 的连接**一直活着**（每小时的服务器时间同步照常），所以可以不靠模型、不靠外网 DNS，直接用她的号给你发一条私聊。

## 它做什么

服务守护（`scripts/services-watchdog.mjs`）每分钟查一次外网：解析 `api.deepseek.com`，再连一下它的 443。

- **最近 10 次里 7 次以上不通** → 记一行日志，并（开了才）给你发一条：「【运维提醒】N 分钟连不上 api.deepseek.com：她连不上模型，现在回不了话、主动消息也发不出。机器人和 NapCat 还在跑。多半是宿主机或虚拟机的网络问题。恢复了我会再说一声。」
- **断了以后最近 5 次都通** → 记一行日志，并（开了才）发一条：「【运维提醒】外网恢复了（断了大约 N 分钟），她又能回话了。」
- 每次断网最多发这两条；窗口不是「连着 10 分钟」。原来的规则在 10-18 这种时好时坏的断网里：第一条告警拖到 02:57 才写（断网 02:05 起），之后当天 02:47–21:26 守护记了 10 段断网，加起来约 17.5 小时；DNS 偶尔成功就把计数清零，碎的段会漏、每段都要先等满 10 分钟。
- 消息是纯文字、以「【运维提醒】」开头，一眼看得出不是她在说话；**不进她的聊天记录**（她不知道自己发过）。你回她，她会当普通聊天回。

## 它不做什么

- 虚拟机整个停了（10-17 02:46 那种）或者 NapCat 没了：这条路发不出去。那种要另外的办法（宿主机侧）。
- 不重启任何服务，不改任何别的东西。
- 发送失败（NapCat 没连上、你不是她号的好友）只在守护日志里记一行，不影响守护。

## 怎么开（要你定）

1. 你要用哪个 QQ 收：**必须是她号（NapCat 登的那个号）的好友**，QQ 才让发私聊。
2. 在虚拟机的 `runtime\bot\alert.json` 里写（这个文件不进 git）：

   ```json
   { "enabled": true, "qq": 你的QQ号, "network": true }
   ```

   没有这个文件，或 `enabled` 不是 `true`，什么都不发。
3. 把代码带到线上：线上目录快进到 `claude/net-alert`（只多脚本和一个不被 Koishi 加载的文件，**不重启 Koishi**），再重启服务守护这个进程（它自己开机 / 登录时由启动脚本拉起）。
4. 第一次开，我会先发一条「【运维提醒】测试」给你确认收得到。

## 验证（10-18）

- 单元：`alert-qq.test.ts` 4 项（配置、发送、各种失败、文字）、`net-watch.test.ts` 7 项（一直通、连续不通、时好时坏、偶尔抖不报、恢复要连续通、可再报、断了多久）；类型检查干净
- 真实 WebSocket 客户端对本地假 NapCat（随机端口）：token 头对、发出 `send_private_msg` 只含文字、回执后断开；连不上的端口返回原因、不抛
- 服务守护 `--once` 自检照常（当时外网正在断，`net: false`）
- **没有**给任何真人发过消息；真发要你定了号码和同意之后
